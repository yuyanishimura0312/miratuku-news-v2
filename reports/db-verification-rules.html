CHAPTER 00 / 序章

なぜルールを明文化するのか

ミラツクは現在66以上のデータベースを運用している。学術知識DBの一部は10,000件規模に達し、実データDBは延べ100万件以上のレコードを収めている。これらが信頼に足るかどうかは、単一の判断ではなく、構築から公開までの全工程に張り巡らされた手続きによって決まる。本文書はその手続きを単一の参照可能な文書として明示する。

大規模言語モデルを用いた知識生産は、いまや調査者一人の手作業を遥かに超える速度で「もっともらしい言説」を量産する。Walters & Wilder（Scientific Reports, 2023）はGPT-4でも引用捏造率が18%に達することを示し、Dahl ら（Large Legal Fictions, 2024）は法務領域で69〜88%、Bhattacharyya ら（Cureus, 2023）は医学領域で47%という値を報告している。つまり、出典の伴わない主張は構造的にハルシネーションと区別できない。この事実は、検証手続きを欠いたAI駆動DBが学術活動の補助になるどころか、誤情報の倍速生成装置に転落する危険を持つことを意味する。

ミラツクのDB群は、検索可能な事実集ではなく意思決定の前提条件として用いられている。連載の前提・コンサルティング提案の根拠・教科書の典拠・政策提言の論拠──いずれの用途においても、エントリの一件が誤っていれば、その上に積まれた判断は連鎖的に揺らぐ。だからこそ、構築の段階で「もっともらしいが検証不能」なデータを排除し、公開の段階で「修正可能な仕組み」を担保する必要がある。

本文書は、これまで46〜66のDB構築で蓄積された経験を、誰が読んでも再現できる形に圧縮したものである。基盤原則（戦略・哲学）、戦術方法論（学術DB7フェーズ／実データDB5段階）、4大品質問題と防止策、横断メタ原則、品質ゲート、チェックリスト、検証体制、実証ケース、運用上の判断トリガーまで、全11章で順に開示する。ここに書かれていないことは原則として実行しない。書かれていることは原則として例外なく実行する。これは「もっともらしさ」と「正しさ」を区別するための、ミラツクとしての公的な約束である。

本文書の位置付け
本ページは databases.html（ミラツク66+DB一覧）の付属文書である。各DBページの末尾と databases.html 最下部から参照可能。新規DB企画時・既存DB再設計時・品質問題発生時に必ず参照する。
CHAPTER 01 / 基盤原則

AI駆動DB構築の12条

戦術的な方法論の上位にある戦略・哲学レイヤー。46DBの成功と失敗、そしてAI研究の先行文献（Walters & Wilder, Dahl, Beel, Vaugrante, Da, CARE Principles 等）から抽出した12の基盤原則を以下に開示する。新規DBの企画、v2再設計、AI駆動リサーチの方針決定は、必ずこの12条を順に通過させる。

PRINCIPLE 01

Claim-First ＋ Provenance 必須付帯

GPT-4でも引用捏造率18%、法務領域69-88%、医学47%。出典のない主張はハルシネーションと構造的に区別できない。

全DBに {claim_id, source_DOI/URL, retrieval_date, verifier, verification_method, confidence_score} を必須付帯。出典なしエントリは構造的に投入不可（Citation Agent ゲート）。lunar-life-db の 800/1,015 検証不能を二度起こさない。

PRINCIPLE 02

件数目標 → 検証通過率KPI への転換

academic-knowledge-db v1 の根本失敗は「件数目標がLLMの古典偏りを増幅した」点にあった。AstaBench（Wang Allen AI 2025）も pass@k 反復による偽精度を警告。

新規DBのKPIは「N件達成」ではなく、(a) citation accuracy ≥85%、(b) フィールド充填率100%、(c) 接続率100%、(d) abstain率（答えない率）の許容明示。件数は副産物として算出する。

PRINCIPLE 03

三層 Verification Stack の標準化

Vaugrante ら（2024, arXiv:2409.20303）が CoT / Self-Consistency / ToT 単体の有意差は6モデル×5技法でほぼ存在しないことを実証。単一プロンプト技法を信奉しない。

Self-Consistency（k≥5）＋ Chain-of-Verification（Dhuliawala 2024）＋ Semantic Entropy（Farquhar Nature 2024）の三層をデフォルト構成とする。個別技法の効果主張は複数seed・複数モデルでの統計検定が前提。

PRINCIPLE 04

完全自律生成は禁止、監督付きアシスタント運用

AI Scientist v1/v2 の独立追試（Beel 2025）で実験42%がコーディング失敗、中央値5件の引用欠損、"Conclusions Here" のプレースホルダ残存が確認された。

Plan / Execute を分離し、計画段階を人間レビュー対象とする。codex-team で並列調査する場合も、最終統合と方針決定はClaude＋人間が握る。生成主体と検証主体を絶対に同一にしない。

PRINCIPLE 05

複数分類体系の並置 — 単一普遍分類を拒否する

distant reading の歴史的後退（Da 2019）、Wikidata の西洋中心バイアス（女性人物22%未満）、Said／Spivak／Mignolo のポストコロニアル批判。「中立の標準分類」は実は政治的選択を隠蔽している。

SEP・仏教教学・儒学・イスラム・先住民・東アジア家制度・近代企業など複数の分類体系を圧縮せずに並置する。属性として優先度・由来・解釈者を保持する（traditional-knowledge-db, philosophy-db, organization-genealogy で実装済み）。

PRINCIPLE 06

Temporal Precision を一級市民に

「正確な日付がない」「時期不明」を欠損として扱うと historical contingency が消失する。Stinchcombe の liability of newness が後知恵で読み替えられる現象と同型の誤りが、年代不明エントリの一括削除で起きる。

全DBで date_precision = exact / year / century / period / unknown を一級市民として扱う。temporal facet で governance / resource / territory / identity の時系列状態を別記録する。

PRINCIPLE 07

CARE ／ OCAP ／ EU AI Act の内製化

EU AI Act（2024/1689）Art.53(c) が訓練コンテンツの著作権遵守を要求、NIST AI 600-1 が12リスクを標準化、CARE Principles（Collective benefit / Authority / Responsibility / Ethics）、OCAP（Ownership / Control / Access / Possession）。traditional-knowledge-db は既に準拠済み。

先住民・コミュニティ・宗教・未公開研究データを含むDBは設計時点で(a)許諾、(b)帰属表記、(c)商用化ポリシー、(d)プライベートエンドポイント運用を決定する。公開LLM API投入禁止データの分類を必ず作成する。

PRINCIPLE 08

タスク特性に応じたエージェント選定

PaperQA2（citation 85.2%）、Anthropic Multi-Agent（+90.2%精度だが15×トークン）、OpenAI Deep Research（GAIA 67.36%）、Coscientist（化学合成）。各システムが得意領域を持ち、万能ツールは存在しない。

文献統合は PaperQA2 型RAG、複数視点並列は Multi-Agent協調、計画的報告は ReWOO 型計画分離、仮説探索は LATS 型木探索。codex-team-playbook の5自動化プロファイル（team / review / research / solo / yolo）の使い分けを習慣化する。

PRINCIPLE 09

Wave 段階展開 — 全完遂を待たない

great-figures-db（Phase 1: 500→2: 2,000→3: 8,000）、academic-db v3 psychology pilot、grant-db Stage 0 が示すとおり、「全完了待ち」は価値を遅延させる。MVPで使い始めることでギャップが判明する。

新規DBは必ず Wave 1 を1〜3日で出す。Wave 1完了→公開→ユーザー利用→ギャップ判明→Wave 2 設計、というループに乗せる。GC-DB（126研究者→Wave 2拡張）、great-figures-db で実証済み。

PRINCIPLE 10

量産より深化 — 既存DBへの接続を優先

66本のDBは既に「相互参照する生態系」を形成している。新規DB追加は限界収益逓減の局面に入っている。逆に既存DBへの接続口（FK / embedding）追加は指数効果を持つ。db-coverage-diagnostic で全16実行領域が Quality ボトルネックであることが判明している。

新規DB提案前に「既存DBのどれかの拡張で実装できないか」を必ず問う。新規が必要な場合も「孤立DB」ではなく「既存DBへのbridge設計」から開始する。cross_db_refs を最低10件設計する。

PRINCIPLE 11

失敗の明示記録 — v1→v2 再設計の教訓を残す

v1→v2 再設計（academic-db v1→v3、miratuku-news→v2、basho-db→public、sangaku-matcher→v2 等）が頻発しているが、再設計理由が README に明文化されていないケースが多い。教訓が暗黙知のままだと後継DBで同じ失敗を繰り返す。

v2 再設計時、README.md 冒頭に「## v1 で何が失敗したか／なぜ v2 を設計したか」セクションを必ず書く。後継DBが教師信号として読める形で残す。

PRINCIPLE 12

ポートフォリオ統治 — クラスター単位の意思決定

66DB を個別最適化すると重複・散逸が増える。逆に5大クラスター（ミラツク／フォーサイト／esse-sense／学術知識／PESTLE・政策）単位で見ると分業構造が成立する。foresight-radar v2 の6ソース統合 dashboard が好例。

個別DB単独より「クラスター統合 dashboard」「クラスター横断 API」「クラスター単位の品質 KPI」を優先する。新規提案はクラスター帰属を明示。クラスター長期ロードマップを持ち、その中での新規DB位置づけを明確化する。

CHAPTER 02 / 戦術方法論

学術DB7フェーズと実データDB5段階

基盤原則を実装に落とす戦術レイヤーは、対象の性格に応じて二系統に分岐する。概念・理論・関係を扱う学術概念DBは7フェーズの方法論を、時系列・指標・観測値を扱う実データDBは5段階の方法論を、それぞれ独立に適用する。両者は並存可能であり、同じエコシステム内で相互参照する。

CHAPTER 03 / 4大品質問題

繰り返し発生する4カテゴリと防止策

イノベーション理論教科書の品質検証で24件の問題を検出した経験から、大規模文書・DBの生成時に繰り返し発生する4カテゴリの品質問題が体系化されている。各問題には固有の発生メカニズムと防止策がある。順に開示する。

A. スナップショット不整合（最頻出・7/24件・29%）

DB改善（重複除去・関係拡充等）の後に、成果物HTMLの数値が古いまま残る問題。成果物に数値をハードコードしており、DBの変更が自動伝播しない構造に起因する。特に「まず成果物を作り、その後DBを品質改善する」というワークフロー順序が直接の原因となる。

防止策：

  1. 成果物生成はDB品質改善の後に行う。DB完成→検証→修正→成果物生成の順序を厳守する
  2. 成果物生成時は必ずDBからリアルタイムでSQLクエリして数値を取得する。ハードコードしない
  3. 成果物生成後にDBを変更した場合、grep -n "旧数値" *.html で全成果物を検索・更新する
  4. 他DBの数値を参照する場合、メモリではなく実DBを直接クエリして最新値を取得する

B. LLMハルシネーション（危険度最高・5/24件・21%）

研究者名×年代×概念名の三つ組で「もっともらしいが誤った」内容を生成する問題。特に大量テキスト生成時にDB参照なしで書くと発生する。LLMの訓練データに基づく「確率的に妥当な」出力が、学術的事実と乖離する。マイナーな研究者や用語の正確な綴り・年代でハルシネーションが起きやすい。

防止策：

  1. 教科書・レポートの本文生成時、各段落で言及する研究者×年代をDBクエリで検証してから書く
  2. 生成後に「全固有名詞×年代」の自動検証スクリプトを実行する：grep -oP '[A-Z][a-z]+.*?\d{4}' | DB照合
  3. 特に警戒すべきパターン：(a) フレームワーク名の正確な表記、(b) 研究者の所属・国籍、(c) 概念の初出年 vs 書籍刊行年 vs 普及年の区別
  4. 日本語固有名詞の漢字変換も要注意（補足→捕捉など同音異字）

C. カバレッジギャップ（構造的問題・8/24件・33%）

各章の「必須理論リスト」なしに生成するため、重要理論の欠落が検出されない問題。エージェントは「知っていることを書く」が「何が欠けているか」は自己検出できない。特に並列チームで分割生成すると、「当然含まれるべき基礎理論」が全チームで見落とされる。

防止策：

  1. 章ごとの必須理論チェックリストをDBクエリで事前生成する：
    SELECT name_en, era_start, key_researchers FROM table WHERE subfield='X' AND significance_score >= 8 ORDER BY era_start
  2. 生成後にチェックリストと突合し、言及されていない必須理論をフラグする
  3. 特にサブフィールドの「創設者」「転換点」「主要批判」の3カテゴリは必ず含める

D. 並列チーム間の不整合（編集問題・4/24件・17%）

複数チームが並列で別章を書くと、テキストの重複・用語の不統一・結語の重複が生じる問題。各チームが独立してLLM生成するため、他チームの出力を参照できないことに起因する。

防止策：

  1. 統合後に必ず重複検出スクリプトを実行する：grep -oP '.{30,}' file | sort | uniq -d
  2. 結語・まとめ・メタファーは最終章にのみ配置し、他章では使わないよう指示する
  3. 統合後にOpusエージェントによる通読レビューを実施し、章間の整合性をチェックする
4大品質問題の分布
イノベーション理論教科書の検証で検出された24件の問題は、A: 29% / B: 21% / C: 33% / D: 17% の比率で分布した。最も頻出するのは「スナップショット不整合」と「カバレッジギャップ」であり、それぞれワークフロー順序と事前チェックリストの欠如という構造的原因を持つ。技術的対策ではなく手順設計の問題として認識する必要がある。
CHAPTER 04 / 横断メタ原則

5箇条と暗黙知7パターン

DB構築・エージェント化・調査解析・連載制作の4領域を横断して、Process Verification 2026-05-15 で抽出されたメタ原則。領域を選ばずに作用する。新規プロジェクト着手時・品質問題発生時にまず参照する5原則を以下に示す。

4-1. 横断メタ原則 5箇条

META 01

生成と検証の分離

実装したエージェントに検証を担わせない。doc-verify、Sentinel、3チーム並列検証など、必ず別主体が検証する。製造補論の3チーム再検証（事実精査50件・DB数値9基・学術批判10件）が代表事例。

META 02

DB完成後に成果物を生成する

Phase 3検証→Phase 4関係構築→Phase 5成果物生成の順序を厳守する。逆順は構造的にスナップショット不整合を生む。イノベーションDBで7件発生した教訓。

META 03

件数目標 → カバー率／検証通過率KPI転換

件数目標はLLM古典バイアスを増幅しハルシネーション量産につながる。代わりに citation accuracy ≥85%、充填率100%、接続率100%、abstain率明示。件数は副産物として算出する。

META 04

削除より flag を優先

synthetic_* / placeholder / paraphrase / likely_synthetic の多軸flagで識別可能性を保持しつつ、明白な「実体ゼロ」のみ削除する。2,763件flag化・4,276件削除の実績。

META 05

Wave 段階展開

全完遂を待たず1〜3日で Wave 1 公開→使う→ギャップ判明→Wave 2 へ。GC-DB（126研究者→Wave 2拡張）、great-figures-db（500→2,000→8,000）で実証済み。

4-2. 暗黙知のメタパターン 7パターン

メモリに未登録だが4領域で繰り返し適用されているパターン。明文化することで判断速度が上がる。

  1. 「未来考察が強ければ既存語が新鮮になる」第一原理 — 形式（DB／連載／エージェント）の精緻化より中身の強度評価が先に来る
  2. v1 の失敗を v2 の README に書く — 教訓継承の最小機構。明文化されないと後継DBで同じ失敗を繰り返す
  3. 並列検証＋直接実行の役割分離 — subagent は読み取り検証に強力、削除・改変はメイン主体が直接実行が確実
  4. メタデータ多軸化による透明性 — data_quality / quality_flag / source_reliability / verification_status / gta_status を最初から組み込む（後付け不可能）
  5. 訂正版を重ねる誠実性 — v1.0→v1.1→v1.2 と訂正履歴を明示公開。ハルシネーション完全防止より「修正可能性」を品質の核に
  6. クラスター統治 vs 個別最適化 — 66DB を個別最適化すると重複・散逸。5大クラスター単位の意思決定が機能する
  7. 派生DB 必須化（連載 ⇄ DB バインド） — 補論執筆時に必ず派生DB（FTT-DB / MTT-DB / PHAI-DB / era-talents-db）を構築。連載は「DBの利用者」かつ「DBの構築動機」として双方向強化

4-3. 3つの核命題

Process Verification 2026-05-15 から導かれた3つの核命題。本文書の根底にある世界観を表す。

  1. 4領域（DB構築・エージェント化・調査解析・連載制作）は独立しておらず、循環構造のなかにある（連載→DB→エージェント→調査→DB v2）
  2. 品質保証は「いつ」「どこで」「だれが」の三点で決まる
  3. 失敗の明文化は次の判断を早くする最大の投資である

5-1. メタデータ多軸化の標準仕様

全DBに以下のメタデータ列を最初から組み込む。後付けは原則不可能（既存エントリの判断材料が失われる）。

data_quality       INTEGER DEFAULT 80      -- 0-100スコア
quality_flag       TEXT                    -- synthetic_* / placeholder / paraphrase 等
source_reliability TEXT DEFAULT 'secondary' -- primary / secondary / tertiary
verification_status TEXT                   -- verified / likely_synthetic / possibly_real
gta_status         TEXT                    -- exact / estimated / interpolated
source_url         TEXT NOT NULL           -- 必須付帯
retrieval_date     TEXT                    -- 取得日
verifier           TEXT                    -- 検証主体
confidence_score   REAL                    -- 0.0-1.0

5-2. 共通スキーマ要件

全DBに以下の3つの共通テーブルを必須とする。これらが存在しないDBは品質ゲートを通過しない。

  • sources テーブル — 出典URL・ライセンス・取得日・取得方法を記録
  • citations テーブル — 各エントリと出典の対応関係（多対多）
  • cross_db_refs テーブル — 他DBとの相互参照（接続キー：国コード／ISO／年／概念名／DOI）
CHAPTER 06 / チェックリスト

ハルシネーション対策チェックリスト

新規DB公開前、既存DB更新前、教科書・レポート生成後に必ず通過させるチェックリスト。担当者は項目ごとに確認の上、結果をログに残す。

6-1. ハルシネーション対策（必須）

  • 全データソース URL に対し WebSearch / WebFetch で実検証ログを残した
  • 「2024年データ」「2025年公開」等の固有時系列factsは一次ソース照合を行った
  • 推定値・補間値は gta_status で明示した
  • レコード由来の出典 URL を 100% 記録した
  • 並列リサーチ完了後は doc-verify エージェントで横断検証を行った
  • 研究者名×年代×概念名の三つ組をDB照合した
  • 固有名詞の自動検証スクリプトを実行した
  • 日本語固有名詞の漢字変換ミスをチェックした

6-2. スナップショット整合性（必須）

  • 成果物生成はDB品質検証の後に行った
  • 成果物の数値は実DBへのリアルタイムクエリで取得した（ハードコードなし）
  • DB変更後、grep -n "旧数値" *.html で全成果物を検索した
  • 他DBの数値は実DBから直接取得した（メモリ参照ではない）

6-3. カバレッジ網羅性（必須）

  • 章ごとの必須理論チェックリストをDBクエリで事前生成した
  • 生成後にチェックリストと突合し、欠落をフラグした
  • サブフィールドの「創設者」「転換点」「主要批判」を必ず含めた

6-4. 並列チーム整合性（必須）

  • 統合後に重複検出スクリプトを実行した
  • 結語・まとめは最終章にのみ配置した
  • 統合後にOpusエージェントで通読レビューを実施した

6-5. ライセンス・倫理（必須）

  • 全データソースのライセンスを明記した
  • CC BY 優先のライセンス選好順序に従って採用判断を行った
  • 有料データ依存度が30%未満であることを確認した
  • 先住民・コミュニティデータは CARE / OCAP に準拠した
  • EU AI Act Art.53(c) の訓練コンテンツ著作権遵守を確認した
  • 公開LLM API 投入禁止データの分類が作成済みであることを確認した

6-6. 公開前最終確認（必須）

  • databases.html にエントリを追加した
  • db-registry.json を更新した
  • ダッシュボード・教科書を公開した
  • analysis-reports.json にレポートを追加した
  • Research Dashboard に完了レポートを保存した
  • 専属エージェント（/xxx-db）を作成した

CHAPTER 07 / ライセンス・帰属・倫理

採用と公開の倫理基準

ミラツクのDBは「公共財」として設計されている。出典の明示・ライセンスの遵守・先住民やマイノリティの権利保護は、品質指標であると同時に倫理的責務である。本章では採用と公開に関する倫理基準を整理する。

7-1. ライセンス選好順序

実データDBに採用する外部データは、次の優先順位で判断する。上位を満たすデータが存在しない場合に限り、下位を検討する。

優先度ライセンス／ソース運用
1CC BY 4.0無条件採用
2CC BY-SA / CC BY 3.0SA条件の派生物管理を設計
3政府公開（CC0相当）無条件採用
4学術登録制（OpenAlex / Crossref 等）レート制限と取得方針を設計
5非営利・要登録非営利明示と帰属表記
6有料採用前に代替検証、依存度30%未満

7-2. CARE Principles / OCAP の適用

先住民・コミュニティ・宗教・未公開研究データを含むDBは、設計時点で次の4点を決定する。

  1. 許諾 — データ提供者またはコミュニティからの明示的同意
  2. 帰属表記 — 提供者・コミュニティ・原典の明示
  3. 商用化ポリシー — 商業利用の可否と条件
  4. プライベートエンドポイント運用 — 公開API禁止データの隔離

traditional-knowledge-db（3,002グループ・36,360項目）は CARE Principles に準拠して設計済み。先住民言語データは Glottolog の言語ID で正規化され、D-PLACE / UNESCO ICH との cross_ref を維持する。

7-3. EU AI Act / NIST AI 600-1 の準拠

EU AI Act（Regulation 2024/1689）Art.53(c) は訓練コンテンツの著作権遵守を要求する。ミラツクDBに収録するデータは、(a) 著作権満了、(b) CC ライセンス、(c) 政府公開、(d) 明示的許諾、のいずれかに該当することを必須とする。

NIST AI 600-1（Generative AI Profile）は12のリスクカテゴリを定義する。本DBは特に Confabulation（ハルシネーション）、Information Integrity（情報整合性）、Information Security（情報安全性）に対する対応をチェックリスト化している（CHAPTER 06 参照）。

7-4. 出典の明示と訂正可能性

ミラツクのDBは「正解集」ではなく「現時点での最善の整理」である。誤りが見つかった場合の訂正経路を公開時に必ず明示する。具体的には：

  • 各エントリに source_url と retrieval_date を必須付帯
  • GitHub issue による訂正提案を受け付ける
  • v1.0→v1.1→v1.2 と訂正履歴を README に明示
  • 削除より flag を優先（識別可能性の保持）
CHAPTER 08 / 検証体制

生成と検証の分離

DB品質を担保する最も重要な構造的措置は、生成と検証の分離である。実装したエージェントに検証を担わせない。これは「自己採点」が機能しないという経験則の言語化であり、横断メタ原則の第1条にも掲げられている。

8-1. 検証チーム構成

学術DBの Phase 6（学術検証）では、3チーム並列・Opus モデルで査読レベルの検証を実施する。

チーム担当範囲主検証項目
A前半章事実正確性・研究者帰属
B中盤章理論的整合性・カバレッジ
C後半章構造的整合性・DB数値照合

8-2. 専属検証エージェント

2026-05-15 新設の専属エージェント群が、各 Stage / Phase の検証を担う。

エージェント担当 Stage / Phase主機能
db-data-verifierStage 2データソース実在検証（URL live・ライセンス分類）
db-scope-designerStage 3MVPスキーマ設計・cross_ref 抽出
db-etl-builderStage 5 Phase 2ETL構築（取得・正規化・投入）

8-3. 並列検証＋直接実行の役割分離

大規模クリーニング Phase 1（2026-05-13）で得られた重要な実装上の知見：subagent は読み取り検証に強力だが、削除・改変はメイン主体が直接実行するほうが確実である。これは subagent のコンテキスト分離による恩恵（並列検証）と、トランザクション一貫性の必要（直接実行）の両立として設計されている。

5並列検証 → 5並列実行の体制
2026-05-13 の DB 大規模クリーニング Phase 1 では、Stage 1 で5並列の Explore subagent が SU / GF / US / ETD / AA を詳細分析し、Stage 2 で Phase 1（低リスク削除）を主体が直接 SQL 実行、Stage 3 で Phase 2/3（Wikidata / Wikipedia / Scholar 補充・置換）を4並列 subagent で実行した。

8-4. Sentinel — 公開前最終ゲート

databases.html への登録、教科書HTMLの公開、dashboard URL のリリース、いずれも sentinel エージェントの承認なしには実行しない。sentinel は次の項目を独立に検証し、いずれか1つでも不合格があれば公開を阻止する権限を持つ。

  • 品質ゲート統一基準（強制項目）の全通過
  • ハルシネーション対策チェックリストの全通過
  • ライセンス・倫理基準の全通過
  • 4大品質問題（A/B/C/D）の各防止策実施確認
  • 専属エージェント・db-registry 登録の完了
CHAPTER 09 / 実証

大規模クリーニング Phase 1 の実績

本章は、これまでに示した原則・方法論・チェックリストが空文ではないことを示すための実証セクションである。2026-05-13 に実施した DB 大規模クリーニング Phase 1 の結果を、定量的に開示する。

9-4. 教訓

本実証から得られた5つの教訓を以下に示す。これらは横断メタ原則および AI駆動DB構築12条 にすでに昇格・反映されている。

  1. メタデータレイヤーが命 — data_quality / quality_flag / source_reliability / verification_status の多軸 flag で透明化する
  2. 削除より flag を優先 — synthetic_* / placeholder / paraphrase 等で識別可能性を保持しつつ、明白な「実体ゼロ」のみ削除する
  3. 5並列検証 → 直接実行 — 並列 subagent は読み取り検証に強力、削除実行は主体が直接が確実
  4. テンプレ検出 — Scientist_NN XX Figure NN NNth Century Leader (Variant N) 日本科学者NN 等の signature を辞書化
  5. API限界 — Codex生成パラフレーズ題目は Crossref / Wayback / arXiv で hit ゼロ。Phase 1 Semantic Scholar 1% を Phase 2 で覆すのは困難

9-5. Wave 1-6 の継続的品質改善

Phase 1 完了後、db-coverage-diagnostic による 21章 × 16補論 × 64DB の3層カバレッジ診断を実施。Variety / Volume / Quality の3軸スコアリングで全16実行領域が Quality ボトルネックであることが判明した。これを受けて Wave 1-6 を実行し、累計 Coverage は 82.4 → 85.6（+3.2pt）に改善した。

CHAPTER 10 / 運用

判断トリガーと再参照

本文書は静的な参照資料ではなく、判断の場で能動的に呼び出される運用ガイドとして設計されている。次の兆候が現れた瞬間、必ず本文書または該当 feedback メモリを再参照する。

10-1. 再参照トリガー

  • 「件数目標」を設定したくなった（→ PRINCIPLE 02 / META 03）
  • 「全完遂を待つ」誘惑が現れた（→ PRINCIPLE 09 / META 05）
  • 同一エージェントに生成と検証を両方任せようとしている（→ PRINCIPLE 04 / META 01）
  • v1 の失敗が明文化されないまま v2 に着手しようとしている（→ PRINCIPLE 11 / 暗黙知2）
  • 個別DB最適化で散逸が進んでいる（→ PRINCIPLE 12 / 暗黙知6）
  • 並列度を9以上に増やそうとしている（→ codex-team-playbook の上限）
  • source_url 欠落のままレコードを投入しようとしている（→ PRINCIPLE 01）
  • LP / Book / Phase D / detail の複数層が並存し、どれが真か揺れている（→ feedback_path_1_lp_as_truth）
  • ユーザー判断待ち事項がブロッカーになっている（→ feedback_default_confirmation）

10-2. 実行系の選択フロー

リサーチ・検証・大量投入の実行系は、状況に応じて動的に選択する。

CHAPTER 11 / 結語

訂正可能性を品質の核に

本文書を通じて開示してきたのは、ハルシネーションを完全に防ぐ魔法ではない。むしろ、ハルシネーションは構造的に避けがたいという前提から出発して、(1) 入口で確率的に減らす、(2) 出口で検出する、(3) 発見後に修正可能な仕組みを残す──という三層の手続きをDB体系全体に組み込むという設計である。

AI駆動の知識生産において、品質の核は「完全無謬性」ではなく「訂正可能性」である。出典なしの主張がハルシネーションと区別できないからこそ、全エントリに source_url を必須付帯する。LLMの自己採点が機能しないからこそ、生成と検証を必ず別主体に分ける。件数目標がバイアスを増幅するからこそ、KPIを検証通過率に転換する。全完遂を待つと価値が遅延するからこそ、Wave 段階展開で1〜3日サイクルに乗せる。これらはいずれも、誤りを構造的に減らしつつ、見つかった誤りを構造的に直せるようにする工夫である。

ミラツクの66+データベース群は、その総体として「現時点での最善の整理」を提示している。各エントリは出典に紐付き、各DBは品質ゲートを通過し、各成果物は4大品質問題のチェックを経ている。それでもなお、誤りはあるだろう。誤りが見つかったときに、隠さず・遅らせず・訂正履歴を残して直す。それが、本文書の根底にある約束である。

本文書は v1.0 として公開する。実運用での発見に応じて v1.1、v1.2 と訂正履歴を重ねていく。原則の追加・削除、品質ゲートの基準値変更、新しい検証エージェントの登場、いずれも本文書の更新を伴う。databases.html の最下部、および各DBページの末尾から、いつでもこの文書に立ち戻れるよう設計されている。検証活動の厳格さとルールのあり方を、開示と訂正の繰り返しによって維持していく。

この文書の運用
本文書は databases.html の最下部からリンクされている。新規DB企画・既存DB再設計・品質問題発生時には、まずこの文書を通読し、該当する原則・方法論・チェックリストを判断の場に持ち込むこと。誤り・抜け漏れ・改善提案は GitHub issue または直接連絡で受け付ける。
