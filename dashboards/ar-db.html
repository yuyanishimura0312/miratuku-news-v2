あるシステムが「育っている」と言えるのは、構成要素の数が増えるからではない。要素どうしが互いを呼びあい、呼ばれた回数がふと「重心」を作り、その重心が外から見える地図になったときである。ミラツク／esse-sense のエコシステムも、ここ半年で 358 という総数を超えるまでに膨らんだ。けれど、数えはじめるまで、誰がどの DB を引用し、どのコマンドがどのエージェントを呼んでいるかは、各 .md ファイルの行間にしか書かれていなかった。

Agent Registry DB（以下 AR-DB）は、その行間を SQLite に抜き出した装置である。~/.claude/agents/・commands/・skills/・rules/ の四つのディレクトリを毎回ゼロからスキャンし、frontmatter からモデル種別・ツール権限・記述を抜き、本文中の /slash 言及を関係グラフに変換する。結果として、473 レコード・1,989 関係・550 件の DB 参照 が机に乗る。

これまで「カタログを作る」というと、エージェントを並べた一覧表を意味していた。けれど、AR-DB がしているのはむしろ逆の編集である。誰が誰を呼んでいるかをたどることで、エージェントの一覧が観察可能な生態系へと反転する。Tier 0 のオーケストレーターは下位のスペシャリストを束ね、メタ層は原則違反を監視し、コマンドは長い正本名にエイリアスを与え、ルールは沈黙のままチーム全員の動きを規定する。本記事は、この生態系の現状報告である。

編集の動機は二つある。第一に、新しいエージェントを作るとき、既に同じ役割の誰かがいないかを確かめたい。第二に、外から見たときにこのチームが何で構成されているのかを、一枚の地図で示したい。両方とも、人の記憶では数か月で破綻する仕事である。AR-DB は、その記憶を肩代わりする外部装置として置かれている。

本稿では、まず数の全容（01）を提示し、続いて三層の階層（02）・領域分布（03）・モデル戦略（04）・ツール使用（05）を読み解く。次に「つながりの密度」（06）と「DB 言及の地図」（07）を見て、誰が呼ばれ、何が語彙基盤になっているかを確かめる。最後にエイリアスの編集行為（08）と /adb 伴走による方法論の三継承（09）に触れ、本DBが自己同期するための仕組み（10）を提示する。

ここから先は、生態系の地図そのものである。

04 ─ 三つのモデルをどう使い分けているか

05 ─ どんな道具を握っているか

08 ─ エイリアスという編集行為

正本名は長くなりがちである。/academic-db-build・/db-coverage-diagnostic。意味は明確だが、毎日使うコマンドとしては身体に重い。そこで、エコシステムは短縮形を後付けする。/adb・/ddb。これらは単なる省略ではなく、「現場の身体感覚に馴染む名前へ翻訳する編集行為」である。

本DBはエイリアスを一つの独立した属性として記録している。コマンドが /正本名 の省略エイリアス という言い回しで宣言されているとき、本文をパースして対応関係を抽出する。結果として、短い名前と長い名前の双方が同じ実体を指していることが、いつでも追えるようになる。

09 ─ /adb 伴走の三継承

本DBは「実データDB」として構築された ─ つまり、学術概念ではなく実在する設定ファイル群を対象とする。しかし、構築の方法論は /academic-db-build v1.1（以下 /adb）の Phase 0-15 から三点を継承している。

第一に、Phase 1 ETL 設計の冪等性。同名の agent と command が並存する事態（adb.md が両ディレクトリに存在する等）を、複合キー（name, agent_type）で許容する。frontmatter 欠落も has_frontmatter フラグで明示記録する。失敗ケースを事前に設計し、ETL を 5 秒以内に終わる軽量さに保つ。

第二に、Phase 3 cross_db_refs の網。本DBは独立した島ではなく、db-registry.json・miratuku-news-v2・MEMORY.md・claude-memory-sync の四基幹システムと cross_db_refs で結ばれている。新エージェント追加 → MEMORY 更新 → 同期 → 本DB再ETL のループが構造的に成立する。

第三に、Phase 13 品質メタの数値化。_quality_metadata テーブルに 12 指標を格納し、いつでも目標値との対比で DB の健康診断ができる。/ddb（Deep DB Diagnostic）と統合可能な 3 軸（Variety／Volume／Quality）形式で記録した。

DEEPER /adb 三継承のポイント ▾
SIGNAL 01

Phase 1 ETL 設計。複合キー (name, agent_type) でエイリアス衝突を許容、has_frontmatter フラグで欠落明示。再ETL は ~5 秒で完了する冪等設計。

SIGNAL 02

SIGNAL 03

10 ─ 自己同期する構造

本DBは一度作って終わりではない。新しいエージェント・コマンド・ルールが追加されるたびに自動的に再同期する。~/.claude/settings.json の PostToolUse hook が 8 件登録されており、対象ディレクトリへの Write／Edit を検知すると auto_update.sh がバックグラウンドで起動する。ETL → ダッシュボード再生成 → miratuku-news-v2 へ配置 → AR-DB repo へ commit／push まで自動で連鎖する。

debounce 10 秒の lock ファイルで多重実行を抑え、失敗してもメインの作業を妨げない設計にした。hook が発火しない経路（直接 vim 編集／他デバイス同期で来た変更）に対しては、~/.claude/rules/agent-registry-update.md がルール化されており、Claude 自身が手動 fallback を判断する。

つまり、本DBは「保守する対象」ではなく「自分自身で最新を保つ装置」である。エコシステムが育つほど、AR-DB はその育成記録を勝手につけてくれる。
