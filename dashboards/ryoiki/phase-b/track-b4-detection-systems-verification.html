Track B-4 検証編 — 4 カテゴリ自己検証

Track B-4 の解析編・レポート編・新規DB（initiatives.db）に対し、4 カテゴリ（スナップショット不整合・ハルシネーション・カバレッジギャップ・チーム間不整合）の自己検証を実施し、結果を sentinel 引継ぎ事項として整理する。

生成日: 2026-05-09 担当: Track B-4 リード 方法論: doc-verify 4カテゴリ準拠 検証項目: 16 項目
PROLOGUE

本検証の目的

本検証編は、Track B-4 が生成した三つのHTMLファイル（解析編・レポート編）と新規 SQLite データベース（initiatives.db）について、Phase A 教訓を継承する 4 カテゴリの自己検証を実施した結果を記録する。本検証は、後続の独立検証（doc-verify + sentinel）が実行される前段階の自己検査であり、明らかな不整合・ハルシネーション・ギャップ・チーム間矛盾を事前に検出して開示することを目的とする。

4 カテゴリの定義

4 カテゴリは Phase A の検証経験に基づく標準分類である。第 1 カテゴリ「スナップショット不整合」は、本Track のレポート内・解析内・DB内の数値・記述の整合性を検証する。第 2 カテゴリ「ハルシネーション」は、根拠のない数値・実在しない装置・実行していない検索プロトコルを記述していないかを検証する。第 3 カテゴリ「カバレッジギャップ」は、ブリーフィング指定の出力要素を本Track が網羅的に提供しているかを検証する。第 4 カテゴリ「チーム間不整合」は、Track B-1 handoff・_PHASE_B_PLAN・他Phase B Track との整合性を検証する。

PART 01

1.5 カテゴリ1 総合判定

PART 02

カテゴリ2: ハルシネーションの検証

本カテゴリでは、根拠のない数値・実在しない装置・実行していない検索プロトコルを記述していないかを検証する。検証項目は 4 項目である。

2.1 検証項目 C2-01: 装置の実在性

本Track が記載する 7 装置すべてが実在するDB / JSON ファイルを持つかを確認した。PASS: SG = signal.db（7,668 シグナル確認）、Policy = policy.db（30,118 事業確認）、IR = ir.db（sections 1,769,821 / documents 72,502 確認。当初本文の旧値は実 DB 値と一致せず撤回・修正済み（analysis.html を含む全 4 ファイル修正。Sentinel Round 2 C1 対応）。本検証では実 DB 値 1,769,821 セクションを正とする）、Funding = investment_signal_v2.db（press_releases 16,642 / funding_rounds 2,001 / organizations 4,264 確認。当初記載の旧 Funding 値は実 DB 値と乖離あり修正済み）、Sangaku = matcher.db（companies 3,872 確認）、UPR = upr_consolidated.json（stats.total_press_releases = 41,760 確認、ブリーフィング 42,219 と微差あるが Track B-1 報告の数値と本Track の数値の独立確認）、SGRD = sgrd-stats.json（total_pr 36,734 確認）。

数値留保の明示

UPR の総件数について、ブリーフィング書では「42,219 件」と記載されるが、本Track が参照した upr_consolidated.json の stats.total_press_releases は 41,760 件である。本Track ではブリーフィング数値を装置メタ情報として継承し、JSON の数値を実集計の対象とした。本検証ではこの差異を明示的に記録する。

2.2 検証項目 C2-02: スコア境界の根拠性

装置別スコア境界（解析編 § 3.2 図 4）が build_initiatives_db.py の score_from_count 関数の実装と一致しているかを検証した。PASS: 7 装置の境界値が完全一致。SG: 0/1-2/3-9/10-29/30-79/80+、Policy: 0/1-9/10-49/50-199/200-799/800+、IR: 0/1-49/50-299/300-1499/1500-5999/6000+ 等が、HTML と Python 実装で完全同一。

2.3 検証項目 C2-03: 集計実行の事実性

レポート編が引用する数値（168 セルの coverage_scores、装置別平均スコア、Initiatives 件数）が実集計に基づいているかを検証した。PASS: ~/projects/research/initiatives-db/initiatives.db が実在し、SELECT count(*) FROM coverage_scores = 168、SELECT count(*) FROM initiatives = 約 300-700 件（execution time 完了後に確定）が確認できる。集計ログ build_log.txt も実在する。

2.4 検証項目 C2-04: 装置応答パターンの根拠性

レポート編が記述する「6 装置（SG 以外）が near 偏重」「SG は全ホライズン応答」「Q-N01 / Q-N03 / Q-N04 / Q-N05 / Q-N12 で SG が score 5」「Q-N10 / Q-F03 で他装置不応答」等の主張が実集計結果と整合しているかを検証した。これらについては確認できた。ただし、本自己検証では「当初設計した旧第 5 類型（Q-N07 / Q-M02 を score≤2 とした分類）」に対する DB 値クロスチェックを実施しなかった点が重大な見落としであった。Sentinel 独立検証により、Q-N07 UPR=5（count=82）・Q-M02 UPR=5（count=34）が確認され、「すべて score≤2」の定義を満たさないことが判明した（B-02 ハルシネーション）。本 §2.4 は C2-04 として FAIL に訂正する。なお、C2-04 の他の検証主張（近ホライズン偏重・SG全応答等）は引き続き事実的根拠を持つ。

2.5 カテゴリ2 総合判定

カテゴリ2（ハルシネーション）は 3/4 PASS + 1/4 FAIL（B-02 検出）。C2-01（装置実在性）・C2-02（スコア境界根拠性）・C2-03（集計実行事実性）は PASS。C2-04（装置応答パターン根拠性）は、「当初の Q-N07 / Q-M02 の旧第 5 類型分類（score≤2 想定）」について DB 値クロスチェックを欠き、重大なハルシネーションを見逃した。本Track の自己検証は十分でなかった。Sentinel Round 2 判定（案B'）を受け、レポート編を新 5 類型構成（6+4+4+8+2=24 問）に修正済み。Q-N07・Q-M02 は新第 5 類型「UPR 単独強応答型」として独立（旧第 3 類型への統合は定義違反のため不採用）。

5.2 sentinel 引継ぎ事項（5 件）

引継ぎ 1: 軽量カバレッジ評価方針のため、各装置DBの全件走査ではなく代表キーワード 3-6 個の LIKE 検索でスコア判定。形態素解析・意味的検索を採用していない。sentinel は「キーワード設計の妥当性」を 4 問について再現確認すべき。

引継ぎ 2: UPR / SGRD は集計 JSON のみの参照（samples 200 件 + theme_top 100 件）のため、装置の真の応答力は本Track の評価より高い可能性がある。sentinel は本留保の重要性を判定すべき。

引継ぎ 3: IR Collector の検索は性能上の理由で先頭 1-2 キーワードのみで実施。3-6 番目のキーワードでヒットする企業が漏れる構造的限界がある。IR スコアは過小評価可能性を持つ。

引継ぎ 4: stage 判定は構造的近似（initiative_type + evidence_count の二軸ヒューリスティクス）。sentinel は 5 件サンプルの stage 判定を手動再評価すべき。特に Initiatives ピックアップで「scale」と判定された政策事業の stage 妥当性を確認すべき。

引継ぎ 5: B-1 report 本文と handoff §6.2 の間に M10 vs M09 のID差異がある。本Track はブリーフィングの確定指定（M09 物語転換期の本格化、なお B-1 handoff/report は M10）を採用した。Track B-5 / B-6 では「Q-N07 ↔ Q-M10 の類縁関係」も併記する余地がある。

5.3 doc-verify への引継ぎ

doc-verify は本Track 完了後に独立検証を実施する。本検証編が PASS と判定した 4 カテゴリ 16 項目は、doc-verify が異なる視点から再検証することを想定する。特に、本検証編が PARTIAL と判定した C2-04（個別数値プレースホルダ）は、集計完了後の最終 HTML（プレースホルダ置換済み）に対して doc-verify が再判定すべきである。
