1.3 装置種別の構造的差異

7 装置は構造的に大きく性質が異なる。SG は研究者が手動で「弱いシグナル」として認定したもののみが収録される少数精鋭型（7,668 件）であり、「言及があれば既に意義あり」と解釈できる。一方 IR は上場企業が法的義務で開示する有価証券報告書からの自動抽出（1.86M セクション）であり、「単に言及される」だけでは弱く、「経営方針・リスク認識として明示される」かが重要となる。Policy は予算事業として「公金が投入されている」という最も具体的な制度反映を示す装置で、件数（30K）と金額の両軸で評価できる。UPR / SGRD は大学・企業の自発的発信として「未来予測」よりは「現在進行中の研究成果」を示す装置である。Funding は「未来への賭け」として VC 投資家のリスク評価を反映する装置である。Sangaku は「企業のニーズと大学のシーズの突合」という構造化された記述を持つ装置である。

1.4 装置間の独立性

7 装置は概ね独立だが、完全独立ではない。例えば Signal DB が拾う「弱いシグナル」のソースに大学プレスリリースや企業IRが含まれることがあり、SG ↔ UPR・SG ↔ IR の相関は完全独立ではない。Sangaku-matcher のソースに UPR・SGRD のプレスリリースの一部が含まれることもある。本Track では「装置間の独立性」は構造的弱点として明示し、ある問いに対する「複数装置の合意」は完全独立 3 装置と読まず、「半独立 3 装置の合意」と読む。解釈

2.3 検索プロトコル

検索プロトコルは装置別に異なる。SG（signal.db）では signal_name と description の OR 検索（LIKE '%kw%'）で件数を取得し、最新 detected_date と composite_score 上位 5 件のサンプルを取得する。Policy DB では FTS5（projects_fts）が利用できる場合は FTS、そうでない場合は name + overview の OR LIKE で検索し、予算 finalized_amount 降順で上位 5 事業のサンプルを取得する。IR Collector は 1.86M セクションの巨大DBであるため、性能上の理由で先頭 2 キーワードのみで text_content LIKE 検索し、最新 period_end と上位 5 ファイラーを取得する。Funding（投資シグナル）は press_releases の title + body の OR LIKE 検索で件数と最新 published_at、上位 5 PR を取得する。Sangaku-matcher は ambition_taxonomy_themes と tech_taxonomy_themes の name + keywords を OR LIKE 検索し、ヒットした theme から代表 5 件を取得する。UPR と SGRD は SQLite ではなく統計 JSON のみが手元にあるため、samples 200 件と top_themes 100 件・gta 48 件の中での textual match 件数を採用する。

2.4 検索プロトコルの限界

本検索プロトコルには三つの限界がある。第一に、LIKE 検索は形態素解析を経ない単純部分一致のため、日本語の活用形・表記揺れを漏らす可能性がある。例えば「気候難民」は拾うが「気候によって追い立てられた人々」は拾わない。第二に、UPR / SGRD は集計 JSON のみで全レコード走査ができないため、件数は theme_top 100 件と samples 200 件の合算となり、装置の真の規模（41,760 / 36,734 件）を反映しない。これは「軽量カバレッジ評価」の構造的制約である。推定 第三に、IR の text_content LIKE 検索は先頭 2 キーワードのみで実施するため、3-6 番目のキーワードでヒットする企業が漏れる。本Trackでは IR スコアの過小評価可能性を留保事項として明示する。

PART 03

スコアリング規則 0-5

本章では、ヒット件数を 0-5 のスコアに変換する規則を装置別に定義する。各装置の収録規模が大きく異なるため、スコア境界も装置別に設定する。

3.1 スコアの意味（共通）

スコア 0-5 の意味は _TRACK_B4_BRIEFING.md の規定に従う。スコア 0 は「装置がカバーしていない」、1 は「言及あるが弱い」、2 は「言及多数だが分析浅い」、3 は「構造化されたデータあり」、4 は「時系列で予測的」、5 は「強力な早期警戒シグナル」である。本Track では「分析の深さ」は装置の自動分類（PESTLE カテゴリ・GTA コード・ambition theme 等）の有無で判断し、「時系列で予測的」は時系列カラム（detected_date / fiscal_year / published_at / period_end）の存在と、最近 2-3 年の継続的レコード増加で判断する。

PART 04

装置別の集計ログ

本章では、24 問 × 7 装置 = 168 セルの集計の主要結果を装置別に整理する。各セルの詳細結果は新規 DB initiatives.db の coverage_scores テーブルに収載される。本章ではその概要のみを示す。

4.1 集計実行の概要

集計は ~/projects/research/initiatives-db/build_initiatives_db.py を 2026-05-09 に実行した。実行時間は約 25 分で、最も時間を要したのは IR Collector（1.86M セクション）の LIKE 検索であった。168 セルすべてに対してスコアと初期 initiatives を生成した。

4.2 装置別の典型的応答パターン

各装置は問いの種類によって応答パターンが大きく異なる。SG（Signal DB）は near 13 問に対してほぼ全問でスコア 3 以上を返し、特に「AIガバナンス」「民主主義」「物語転換」「場所性回帰」等の真M / 準M 由来問いに対して score 4-5 の強い応答を返す。一方 very-far 2 問（Q-V02 / Q-V06）は score 2-3 に留まる。これは Signal DB が「現在進行中の弱いシグナル」を扱う装置として、far / very-far の問いに直接応答する設計ではないことを反映する。

UPR / SGRD（PR 系装置）は near の研究系問い（Q-N07 科学AI、Q-N08 自律AI、Q-N10 非西洋認識論）に対して中程度（score 2-3）の応答を返すが、規範系問い（Q-N09 主体・人格、Q-N12 values、Q-N13 教育ラグ）に対しては score 1-2 に留まる。これは PR 系装置が「研究成果の発信」を扱うため、規範的問いの観測には不向きであることを反映する。

Policy DB は near の制度系問い（Q-N02 AI制度反作用、Q-N05 民主主義、Q-N06 気候災害、Q-N13 教育改革）と mid の制度系問い（Q-M02 / Q-M04 / Q-M12）に対して score 3-4 の強い応答を返す。これは政策事業が「制度反映」の最も具体的な観測装置であるためである。一方、概念系問い（Q-N09 / Q-N11 / Q-V07）に対しては score 0-1 に留まる。

IR Collector は near / mid のすべての問いに対して何らかの記述を持つ可能性が高いが、score の分散は大きい。特に AI 系問い（Q-N01 / Q-N02 / Q-N07 / Q-N08）と気候系問い（Q-N06 / Q-M08 / Q-F01）は企業の経営方針・リスク認識として明示されるため score 4-5 に達するが、規範系・神話系問いは IR の対象外であり score 0-1 に留まる。

Funding（投資シグナル）は near の技術系問い（Q-N01 / Q-N07 / Q-N08）と mid の医療系問い（Q-M10 創薬AI に類する Q-N07 拡張）に対して score 3-4 の応答を返す。VC 投資は「未来への賭け」を反映するため、AI・バイオ・気候技術の問いには強い応答を示す。一方、規範系・制度系問いに対しては score 0-2 に留まる。

Sangaku-matcher は ambition_taxonomy_themes 33 件と tech_taxonomy_themes 40 件の構造化分類が中心であり、各問いに対する応答件数の分散が小さい（0-5 件程度の theme ヒット）。33 ambition × 100 + 40 tech × 80 の擬似スケーリング後、AI / 環境 / 教育系問いに対して score 3-4、規範系問いに対して score 0-2 となる。

4.3 集計ログの保存場所

168 セルすべての集計ログは ~/projects/research/initiatives-db/build_log.txt に保存される。各行は「問いID\t装置名\tscore=N\tcount=N\tlatest=YYYY-MM-DD」形式である。SQL レベルの詳細は initiatives.db の coverage_scores テーブルから直接抽出可能である。

集計ログの利用

本集計ログは、Track B-5（B-3 問い × B-4 装置の動き測定）と Track B-6（Phase B 統合）が直接参照する。特に Track B-5 では本Track のスコアを「動きのある hot zones / 動きのない dead zones」の弁別に使用し、score ≧ 3 のセルを「動きあり」、score ≦ 1 のセルを「動きなし」と暫定的に判定する。

PART 05

Initiatives DB の設計

本章では、本Trackで新規構築した SQLite データベース initiatives.db のスキーマ設計を提示する。本DBは Phase B Track B-5 / Track B-6 の入力となり、ミラツク全体での「すでにある取り組み」の領域別マップとして機能する。

5.1 スキーマ概要

新規DBは 4 テーブルで構成される。questions（問いマスタ、24 行）、detection_systems（装置マスタ、7 行）、coverage_scores（カバレッジマトリクス、168 行）、initiatives（個別取り組みレコード、目標 240-720 行）の四つである。スキーマは _TRACK_B4_BRIEFING.md 第 5 節の指示に従う。

5.2 スキーマ詳細

CREATE TABLE questions (
    question_id TEXT PRIMARY KEY,
    question_text TEXT,
    horizon TEXT,    -- near / mid / far / very-far
    ctl1 TEXT        -- V / S / T / Eco / Env / G
);

CREATE TABLE detection_systems (
    id INTEGER PRIMARY KEY,
    name TEXT UNIQUE,
    type TEXT,
    db_source TEXT,
    total_records INTEGER
);

CREATE TABLE coverage_scores (
    id INTEGER PRIMARY KEY,
    question_id TEXT,
    system_name TEXT,
    score INTEGER,         -- 0-5
    evidence_count INTEGER,
    latest_signal_date TEXT,
    notes TEXT,
    FOREIGN KEY (question_id) REFERENCES questions(question_id)
);

CREATE TABLE initiatives (
    id INTEGER PRIMARY KEY,
    question_id TEXT,
    organization TEXT,
    initiative_name TEXT,
    initiative_type TEXT,    -- research / product / policy / investment / partnership
    stage TEXT,              -- ideation / experiment / pilot / scale / mature
    horizon TEXT,
    source_db TEXT,
    source_id TEXT,
    summary TEXT,
    FOREIGN KEY (question_id) REFERENCES questions(question_id)
);

5.3 stage カラムの判定ロジック

initiatives テーブルの stage カラムは「ideation / experiment / pilot / scale / mature」の 5 段階で記録する。判定ロジックは initiative_type と evidence_count の組み合わせで決定される。policy 型は evidence_count > 100 で「scale」、それ未満で「pilot」と判定する。investment 型は evidence_count < 30 で「experiment」、それ以上で「scale」と判定する。research 型は基本「experiment」、product 型は「pilot」、partnership 型は「pilot」と判定する。これは構造的近似であり、個別の正確な stage 判定は装置別の追加メタデータが必要となる。推定

5.4 source_db / source_id の保存

各 initiative は元のソース装置と元レコードの ID を保持する（source_db = SG/UPR/SGRD/Policy/IR/Funding/Sangaku、source_id = 元DBのプライマリーキー）。これにより、Track B-5 / B-6 で「ある initiative がどの装置から検出されたか」を遡及できる。例えば SG のシグナル ID 1234 から導出された initiative は source_db = "SG", source_id = "1234" として保存される。

5.5 DB の利用パターン

本DBの主要な利用パターンは三つである。第一は「カバレッジマトリクス出力」で、SELECT question_id, system_name, score FROM coverage_scores で 168 セルを取得し、HTML ヒートマップとして可視化する。第二は「装置別の予測的応答力スコア」で、SELECT system_name, AVG(score), AVG(evidence_count) FROM coverage_scores GROUP BY system_name で各装置の平均スコアを算出する。第三は「ある問いに対する取り組み一覧」で、SELECT * FROM initiatives WHERE question_id = 'Q-N01' ORDER BY source_db で領域別のピックアップを取得する。

PART 06

4 ホライズン × 7 装置の集計

本章では、24 問を 4 ホライズン（near 13・mid 6・far 3・very-far 2）でグループ化し、7 装置のスコア平均を算出した結果を提示する。詳細はレポート編 第 2 部・第 3 部に収載する。

6.1 ホライズン別の装置応答力

ホライズン別に集計すると、near は 7 装置すべてが何らかの応答を返すゾーンで、最も装置応答が厚い。mid は SG と Policy が中心となり、far / very-far は SG が中心、他装置の応答は弱い。これは「現在進行中のシグナル」を扱う装置の構造的限界を反映する。詳細な数値はレポート編 図 5 で提示する。

6.2 装置別の問い応答力

装置別に 24 問の平均スコアを算出すると、SG が最高、IR と Policy が中位、UPR / SGRD / Funding / Sangaku が下位となる。これは装置の「予測的応答」設計の差を反映する。SG は弱いシグナル発見が設計目的なので、24 問の問い空間に対して幅広く応答する。IR / Policy は経営記述・予算事業として「現在動いている領域」を反映する。UPR / SGRD は研究成果の発信として「すでに達成された成果」を反映するため、未来予測的な問いには応答が弱い。Funding は VC リスク評価として技術系問いに集中する。Sangaku は ambition / tech theme として既知のカテゴリにマッピング可能な問いに集中する。詳細はレポート編 第 4 部で提示する。

6.3 装置間の補完関係

装置間の補完関係は、ある問いに対する「装置間スコア相関」と「装置間カバレッジ重複」の二つで分析できる。例えば Q-N01「AIガバナンス」は SG・Policy・IR・Funding の 4 装置で score 3+ となり、相互補完的なカバレッジを提供する。一方 Q-N09「主体・人格」は SG のみが score 3+ で、他装置は score 1-2 に留まり、SG 単独依存の構造を持つ。詳細な補完関係パターンはレポート編 第 5 部で 5 パターンとして類型化する。

PART 07

解析上の留保

本章では、本解析編の方法論的留保と、後続Track（B-5/B-6）への引継ぎ事項を率直に開示する。

7.1 軽量カバレッジ評価の構造的限界

本Track の方法論は「軽量カバレッジ評価」であり、各装置DBの全件走査ではなく代表キーワード 3-6 個の LIKE 検索でスコアを判定する。この方法論には四つの構造的限界がある。第一に、形態素解析を経ない LIKE 検索のため、表記揺れ・活用形を漏らす。第二に、UPR / SGRD は集計 JSON のみの参照で全レコード走査ができない。第三に、IR の検索は性能上の理由で先頭 2 キーワードのみで実施する。第四に、スコア境界は装置の収録規模を反映するが、「真の質的差」を直接反映するわけではない。

7.2 装置間の独立性に関する留保

本Track では 7 装置を「独立な観測装置」として扱うが、実際には部分的相関がある。Signal DB のソースに UPR・SGRD・IR の一部が含まれる可能性、Sangaku-matcher のソースに SGRD・UPR の一部が含まれる可能性がある。本Trackでは「装置間の独立性」を完全独立と読まず、「半独立」と解釈する。これは Phase A Track 8 が指摘した「文脈別の独立性表現処理」の継承であり、装置間スコア合意は「独立 N 装置の合意」ではなく「半独立 N 装置の合意」と読む。

7.3 stage 判定の構造的近似

initiatives テーブルの stage カラムは構造的近似で判定される（initiative_type + evidence_count の二軸ヒューリスティクス）。個別の正確な stage 判定は装置別の追加メタデータが必要となる。例えば、ある政策事業が「scale」段階なのか「pilot」段階なのかは、政策事業の予算規模・実施期間・他事業との関係で決定されるべきものだが、本Track では evidence_count > 100 を構造的閾値として使用する。推定

7.4 24 問の網羅性に関する留保

本Track が評価する 24 問は、Track B-1 § 6.2 で B-4 対象として指定された問い群である。この 24 問の選定は B-1 が「変化検出装置で観測可能か」の事前判断で行ったが、実際の評価で「観測不可能」と判明する問いがある可能性、また B-1 が指定外とした 17 問の中にも観測可能な問いがある可能性がある。本Track では 24 問の評価結果を踏まえ、Q-N09 / Q-N11 / Q-V07 等の score 0-1 集中問いについては「装置がカバーしていない構造的事実」を発見として明示する。

7.5 sentinel 引継ぎ事項

本解析編から sentinel への引継ぎ事項は四つである。第一に、本Track の検索プロトコルは LIKE 検索ベースであり、形態素解析・意味的検索を採用していない。検証編で「キーワード設計の妥当性」を 4 問について再現確認すべき。第二に、UPR / SGRD は集計 JSON のみの参照のため、装置の真の応答力は本Track の評価より高い可能性がある。検証編でこの留保を明示すべき。第三に、stage 判定は構造的近似である。検証編で 5 件サンプルの stage 判定を手動再評価すべき。第四に、Track B-5 への引継ぎ書では、score ≧ 3 のセル数と score ≦ 1 のセル数を hot/dead zones の暫定判定として提供すべき。
