# 領域策定プロジェクト — 横断プロトコル
*Methodology Lead 文書 / Wave 0.5 確定版 / 2026-05-09*

本文書は、9トラックが共通の方法論で動くための横断プロトコルを定義する。Track 1（FK Foresight）の実装で確立されたパターンを基準とし、後続8トラック（megatrend／SI Framework／統合分析／IR・投資／GPT-QoL／CLA／PESTLE／Tech Acceleration等）が迷わず使える具体性で記述する。本書の規定と `_BRIEFING.md` が矛盾した場合、本書を優先する（仕様は契約書である）。

---

## 1. ホライズン定義

### 1.1 主軸の四基準年
領域策定プロジェクトの問いは **2030 / 2050 / 2070 / 2100** の四基準年で構造化される。各基準年は単年ではなく、その前後を含む「時間幅」として解釈される。

### 1.2 共通スパン定義（必須採用）

| スパン名 | 範囲（含端） | 別名 | 解釈 |
|---|---|---|---|
| `near` | 2026-2035 | 2030近傍 | SDGs／Industry 4.0／企業中期計画と接続する〈実装可能な未来〉 |
| `mid` | 2036-2055 | 2050遠期 | 構造転換目標／ネットゼロ／長期社会保障の射程 |
| `far` | 2056-2080 | 2070長期 | 世代交代後の社会・気候軌道 |
| `very-far` | 2081-2100 | 2100超長期 | 人口統計・気候モデルが支配的、思考対象が限定的 |
| `beyond` | 2101以降 | — | 個別研究のみ。集計時は除外可。 |
| `unspecified` | 年未明示 | — | DBごとの未明示率を必ず併記する |

### 1.3 重複領域の扱い
- 2030は `near` の上端、2031からは `mid` の入口。基準年そのものを集計する場合、`L-09`同様に **単年集計** を別系列で示す。
- 2050は `mid` の上端、2051からは `far` の入口。
- いずれの境界も「**含端方式**」（2030は `near` に含む）で統一する。境界をまたいで誤差±1年が出る場合、必ず明示する。
- DB側のラベル名（FKの `near_2030 / medium_2040 / far_2050plus` など）と本書の共通スパン名が異なる場合、analysis.html 第1〜3章のいずれかで **マッピング表** を提示する。

### 1.4 ホライズン未指定率の必須開示
予測または記録に年情報が無いものの比率は、analysis.html の冒頭近く（第1または第3章）で必ず開示する。例：FKの場合「年明示は3,628件で予測全体の15.6%、未明示が84.4%」。**未明示率を伏せた上でホライズン分布を語ることは禁止**する。

## 2. テーマ分類軸（共通スキーマ）

### 2.1 三層タクソノミー
9トラックの主軸DBは、それぞれ独自のテーマ体系（FKの3層323項目／VeSTEG／GTA48／PESTLE6軸／CLA4層／SI Drayton×6軸 等）を持つ。本プロジェクトでは、これらを **Track 10統合用の共通レイヤー（CTL: Common Theme Layer）** にマップする。

| レイヤー | 名称 | 項目数目安 | 用途 |
|---|---|---|---|
| CTL-1 | メガドメイン | 6 | 最上位カテゴリ（後述） |
| CTL-2 | テーマ | 30前後 | 章立てや表頭に用いる粒度 |
| CTL-3 | サブテーマ | 100-200 | TOP10根拠や問いの仮設で参照 |

### 2.2 CTL-1 メガドメイン（6カテゴリ・必須）
VeSTEG の6軸を基準とし、PESTLE/GTAとマップ可能なように設計した。

| CTL-1 コード | 日本語 | 包含する VeSTEG / PESTLE / GTA48 |
|---|---|---|
| `CTL-V` | 価値観・倫理・文化 | VeSTEG: values / GTA48: 教育・宗教・芸術 |
| `CTL-S` | 社会・人口・コミュニティ | VeSTEG: society / PESTLE: Social / GTA48: 人口・移住 |
| `CTL-T` | 技術・知 | VeSTEG: technology / PESTLE: Technological / GTA48: AI・量子・バイオ |
| `CTL-Eco` | 経済・労働・産業 | VeSTEG: economy / PESTLE: Economic / GTA48: 産業構造・労働 |
| `CTL-Env` | 環境・資源・気候 | VeSTEG: environment / PESTLE: Environmental / GTA48: 気候・水・食料 |
| `CTL-G` | ガバナンス・地政学・制度 | VeSTEG: governance / PESTLE: Political+Legal / GTA48: 国際秩序 |

### 2.3 命名規則
- 全章タイトル・図表タイトルでは、**日本語名を主表記**とし、CTL-1コードを括弧内に併記してよい（例：「テクノロジー・デジタル（CTL-T）」）。
- DB固有のテーマ名（FK の "0101 人工知能・機械学習" 等）はそのまま保持し、CTL-3 として参照する。
- 集計表の表頭は、各トラック内では DB固有名でよいが、Track 10 統合時には CTL-2 名に正規化する。

### 2.4 マッピング表の必須化
各トラックの analysis.html に、以下の節を必須で含める。

```
### 本Trackのテーマ体系と CTL-1 のマッピング
| DB固有テーマ | CTL-1 | 備考 |
|---|---|---|
| (DB側のL1またはトップ層を全行) | CTL-V/S/T/Eco/Env/G | 多重該当・割当不能の説明 |
```

## 3. TOP10評価指標統一定義

### 3.1 三軸の名称と略号（厳守）
- **W（重要度 / Weight）**：領域策定における優先度
- **C（確からしさ / Certainty）**：データ根拠の確実性
- **M（ミラツク親和性 / Miratuku-fit）**：知識運動体としてのミラツクの強み（領域横断・対等な探究・暗黙知の形式知化）と接続できるか

各軸 **1〜5の5段階**、合計15点満点でランキング。同点は「戦略的相補性（密度／空白の交互配置）」で順位を付与する（Track 1 第5章の方式を踏襲）。

### 3.2 5段階尺度の定義文（全トラック共通）

#### W（重要度）
| 値 | 定義 |
|---|---|
| 5 | 領域策定全体の中核問い。複数Trackで重要性が確認され、ミラツク事業の方向性を直接左右する。 |
| 4 | 主要な問いの一つ。1〜2Trackで強く確認され、ミラツク事業との関連が明確。 |
| 3 | 重要だが射程が限定的。特定Track内では強いが横断性が中程度。 |
| 2 | 補助的な問い。他領域の前提条件として現れる。 |
| 1 | 周辺的。記録には残すが優先度は低い。 |

#### C（確からしさ）
| 値 | 定義 |
|---|---|
| 5 | 主軸DBで予測・言及1,000件以上 **かつ** 出典の三層性（学術／国際機関／政府または同等3系統）を満たす。 |
| 4 | 100-999件 **かつ** 二層以上の出典系統。 |
| 3 | 30-99件、または出典が一系統に偏る。 |
| 2 | 10-29件。データ薄い。 |
| 1 | 10件未満、または「ほぼゼロ」。空白戦略のためにのみ採用可。 |

#### M（ミラツク親和性）
| 値 | 定義 |
|---|---|
| 5 | ミラツクの三本柱（領域横断・対等な探究者・暗黙知の形式知化）のうち2つ以上に直接接続。 |
| 4 | 三本柱のいずれか1つに直接接続。 |
| 3 | 既存ミラツク事業（CRM／メンバーシップ／場所性／企業対話 等）と接点あり。 |
| 2 | 間接的接続。説明を要する。 |
| 1 | 接続が薄い。除外候補。 |

### 3.3 戦略タグ（必須付与）
TOP10の各領域には以下のいずれかを付与する。
- **密度戦略**：主軸DBで濃く扱われている領域。ミラツクが「上に立つ独自視点」を打ち出す対象。
- **空白戦略**：主軸DBで薄い／ゼロの領域。ミラツクが「未開拓フロンティア」として開拓対象。
- **接続戦略**（任意）：他Trackとの架橋がTOP10入りの主因である場合。

Track 1のTOP10は密度6・空白4の構成。各トラックは自由に比率を選んでよいが、**密度のみ または 空白のみ で構成することは原則禁止**（少なくとも2種を含める）。

## 4. DB集計ログ標準フォーマット

### 4.1 クエリID命名規則
- 形式：`L-{NN}` または `L-{NN}{a-z}`（連番＋必要時アルファベット枝番）
- 各トラック内で **L-01 から連番** で開始。Track 1 は L-01〜L-63 を使用済。Track 2 以降も自トラック内で L-01 から再採番してよい（トラック間でID衝突は気にしない）。
- 集計の修正版は枝番で示す（例：`L-35` → `L-35c`、Track 1の地域分類クリーン版）。

### 4.2 必須記載項目
analysis.html 末尾の「DB集計ログ（付録）」セクションは、**各クエリにつき以下を記載**：
1. **見出し**：`<h3>L-NN: {集計の主旨}</h3>`
2. **SQL本文**（または使用ツール名）：`<pre><code>` ブロックで表示
3. **抽出件数または主要結果**：SQLコメント `--` または直後に併記
4. **本文中の参照箇所**（推奨）：「第X章で使用」のメモ

例（Track 1 L-09 の形式）：
```
<h3>L-09: predictions.time_horizon_year 単年TOP30</h3>
<pre><code>SELECT time_horizon_year, COUNT(*) cnt FROM predictions
WHERE time_horizon_year IS NOT NULL
GROUP BY time_horizon_year ORDER BY cnt DESC LIMIT 30;
-- 2030(2046), 2050(478), 2025(282), 2040(186), 2035(153), ...</code></pre>
```

### 4.3 本文中の参照記法（必須）
analysis.html 本文の主要主張には、以下のいずれかで根拠IDを明示する：
- インライン軽量タグ：`<span class="tag-evidence">※集計L-09</span>`（Track 1で使用）
- 文末括弧記法：`（集計L-09）`
- 表番号併用：`（表3／集計L-19）`

「Generative AIが…」のような **数値・固有名詞・引用** には、原則すべて根拠IDを付ける。エッセイ的な解釈段落には不要。

### 4.4 SQL以外の集計手段
専門エージェント（`/foresight-kb`、`/cla` 等）経由の集計や、Pythonスクリプト出力もログ対象。SQLが書けない場合は以下で代替する：
```
<h3>L-NN: {主旨}</h3>
<p>取得方法: <code>/foresight-kb</code> エージェント経由 / クエリ "{自然言語クエリ}" / 取得 2026-05-09</p>
<pre><code>-- 結果サマリ
{主要数値の記述}</code></pre>
```

## 5. 【推定】【解釈】【未検証】タグ使用ガイド

### 5.1 三タグの定義

| タグ | 定義 | 使用例 |
|---|---|---|
| **【推定】** | DBに直接の値はないが、隣接データ・補助情報から数値的・構造的に推測した記述 | 「FKの57メガトレンドは、megatrend DBの18体系を**【推定】**内包する」 |
| **【解釈】** | データから読み取れる構造に対する**意味付け**。数値的事実から論理的に導出されるが、別の解釈もあり得る | 「2030近傍に予測が集中するのは、SDGs / 企業中期計画への**【解釈】**接続志向の表れである」 |
| **【未検証】** | 主張の蓋然性は高いが、本トラックでは検証していない事項 | 「分類器が values 系を取りこぼしている可能性が**【未検証】**ある」 |

### 5.2 使い分けの原則
- **【推定】** は「数値が無い／隣接値から外挿した」場合。後段で実DBを引けば確認できる性質のもの。
- **【解釈】** は「数値はあるが、その意味の取り方は一意でない」場合。複数の解釈を許容する留保。
- **【未検証】** は「真偽の判定そのものを保留」する場合。Track内で時間／スコープが足りなかった事項。

### 5.3 タグの可視化（HTML実装）
本文中で以下のように記述：
```html
分類器の弱さの可能性（<strong>【未検証】</strong>）。
```
または、Track 1 で使用された軽量タグ：
```html
<span class="tag-est">推定</span> 内包する
```

### 5.4 タグの集約（必須）
verification.html の「カバレッジギャップ」または「研究の限界」セクションで、**本Trackで【未検証】とした事項を一覧化**する。これにより独立検証エージェントが追跡対象を把握できる。Track 1 は7件の「要追跡」事項として一覧化済（参照モデル）。

### 5.5 禁止表現
- 「らしい」「と思われる」「だろう」など曖昧な伝聞調は、上記三タグで置換する。タグなしの曖昧表現は doc-verify で差戻し対象。

## 6. 9トラック相互参照規則

### 6.1 他トラック参照記法
本文中で他トラックに言及する際は、以下の統一記法を用いる：
- **Track番号＋主軸DB略称**：例「Track 2（megatrend DB）」「Track 7（CLA DB）」
- 該当HTMLが既に存在する場合、相対パスでリンク：`<a href="track2-megatrend-report.html">Track 2 レポート</a>`
- まだ未着手のTrackについては、Wave別運用（_TEAM.md 記載）を踏まえて「Wave 1で実装予定」等を併記。

### 6.2 統合スキーマ連結ID
Track 10統合のため、各トラックは以下の **連結ID** を report.html 末尾の「他トラックとの接続点」セクションで明示する：

```
### Track 10 統合用連結ID
- 主軸DB: {dbid}
- 強みホライズン: near / mid / far / very-far のいずれか（複数可）
- 強みCTL-1: V / S / T / Eco / Env / G（複数可）
- 補完が必要な領域: {他Track番号と理由}
- 提供できる補完: {他Track番号と提供内容}
```

### 6.3 接続点の記述粒度
「Track Xとの接続点」は **抽象的な親和性ではなく、具体的な集計・概念マッピング** で記述する。
- 良い例：「FKの57メガトレンドのうち、megatrend DB（Track 2）の18体系にマッピング可能なものを Track 2 側で抽出する」
- 悪い例：「Track 2 と関連が深い」

### 6.4 矛盾発見時の処理
他Trackの主張と本Trackの主張が矛盾する場合：
1. verification.html の「カテゴリ4: チーム間不整合」セクションで明示する。
2. **どちらが正しいかを本Trackで断定しない**。両論を提示し、Track 10統合時の判断材料とする。
3. メイン会話（継続オーケストレーター）が最終判定する。

## 7. 数値スナップショット不整合の扱い

### 7.1 三系列差の標準処理
DB由来の数値は、**複数のスナップショットが並存する**可能性がある。Track 1 で発生したFKの「機関数 309 / 323 / 463」「レポート数 45,323 / 50,322 / 76,548」問題を典型例とする。

### 7.2 三系列の名称（共通）
| 系列名 | 定義 | 取得元の例 |
|---|---|---|
| **ブリーフィング値** | `_BRIEFING.md` または事前資料に記載された値 | 309機関（生成時刻不明） |
| **公開値（ダッシュボード値）** | 既存の公開ダッシュボード（dashboard.html等）に埋め込まれた値 | 323機関（dashboard.html DATA、generated_at 2026-04-24） |
| **DB実値** | analysis.html 生成時点での SQLite 直接照会結果 | 463機関（foresight.db、2026-05-09 実行） |

### 7.3 標準処理フロー（必須）
analysis.html の **第1章** で以下の三段処理を行う：

1. **三系列の併記**：表形式で各系列の値・取得元・取得日時を示す。
2. **採用値の宣言**：「本レポートでは {系列名} を一次値として採用する」と明示。原則として **DB実値（最新）** を採用する。
3. **差異の意味解釈**：差分が何を反映するか（収集パイプラインの後続実行・LLM抽出の遅延等）を【解釈】タグで述べる。

### 7.4 verification.html での再記録
verification.html の「カテゴリ1: スナップショット不整合」で、上記三系列を再掲し、各系列の判定（問題なし／要追跡／要修正）を付与する。Track 1 は「問題なし（明示的に時系列を記録済）」とした。

### 7.5 Track 10 統合時の基準値選定
本書では基準値選定をオーケストレーター（メイン会話）に委ねる。各トラックは三系列を必ず開示し、**統合時に基準値を変更可能な状態**を保つ。

### 7.6 単一系列しか得られない場合
公開ダッシュボードがない、または `_BRIEFING.md` に該当数値がない場合、その旨を明示し、得られる系列のみで進めてよい。

```
### 機関数のスナップショット
- DB実値: 12,958人（era_talents.db、2026-05-09実行）
- ブリーフィング値: 同値
- 公開値: 別途公開ダッシュボードなし
- 採用: DB実値
```

## 8. 判定区分（共通4階層）

verification.html の各検査項目には、以下4階層のいずれかを付与する（Track 1 で確立）。

| 判定 | CSS | 意味 | 後続アクション |
|---|---|---|---|
| **問題なし／一致** | `.sev-low` | 検査クリア。 | アクション不要。 |
| **要解釈** | `.sev-mid` | 数値・構造に問題はないが、解釈に注意を要する。 | report.html で注記。 |
| **要追跡** | `.sev-mid` | 本Trackでは判定保留。後続Trackまたは Track 10 で再検証。 | verification末尾で一覧化。 |
| **要修正** | `.sev-mid` | report.html で訂正必須。 | report.html 当該箇所で修正。 |
| **構造的ギャップ** | `.sev-high` | DBの構造的限界。本Track単独で解消不能。 | report.html「研究の限界」セクション必須記載。 |
