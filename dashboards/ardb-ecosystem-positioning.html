AR-DB エコシステムの運用特徴と先行事業との関係性

ミラツク/esse-sense DB エコシステム（AR-DB + 167 DB / 448 アセット）の運用特徴を、世界の優れた先行事業 ConceptNet・AWS Agent Registry・ChatDev・OpenAlex・WeKnora 等との関係性に位置づけて 5,000 字で解説する。

2026-05-18 作成 Yuya Nishimura + Claude Opus 4.7 5,000字 / 6章
PROLOGUE

立ち位置 ─ 先行の地平に立つ

本エコシステムは、世界の知識基盤プロジェクトが切り拓いた地平の上に立っている。ConceptNet が 27 年、Wikidata が 14 年、OpenAlex が 4 年、AWS Agent Registry が 2 年と、各分野には強力な先行事業がある。本レポートは「世界初」を主張するためのものではない。各先行事業と並ぶ輪郭で、本エコシステムが採った設計選択と運用特徴を 6 領域に分けて記述する。各章で先行事業を必ず参照し、その地平の上で何を選択したかを明示する。

CHAPTER 01

領域別独立 DB 連邦 ─ ConceptNet・ASER のパターン C を継承する

ConceptNet（MIT Media Lab, 1999-）は、1999 年に Push Singh と Marvin Minsky が始めた Open Mind Common Sense を起点に、27 年をかけて 3,400 万エッジ・304 言語の常識知識グラフを構築した。Robyn Speer 主導の AAAI 2017 論文で世界的に認知され、Numberbatch 単語埋め込みは SemEval-2017 で複数言語の意味類似度タスクを総合優勝した。ConceptNet が確立した設計は、領域別独立テーブル × 34 関係型による接続という「パターン C 連邦化」である。ASER（HKUST）がイベント領域でこれを継承し、USC ISI の CSKG（2021）は ConceptNet・ATOMIC・Wikidata-CS・WordNet・Roget・Visual Genome を統合した 6 ソース連邦の代表例となった。

本エコシステムも同パターン C に分類される。167 の独立 SQLite DB が、各々独自スキーマを保ち、cross_db_refs テーブルで意図的に接続される。差異はひとつ。ConceptNet が汎用 34 関係型に統一するのに対し、本エコシステムは領域別に関係型を正規化する。物理学概念 DB では predecessor / successor / theoretical_basis、人物 DB では influenced_by / branched_from / merged_with、産業 DB では supplied_by / competed_with といった具合に、領域に最適化された関係語彙を持つ。これは ConceptNet が獲得した「汎用性」を犠牲にする代わりに、「専門性の解像度」を取る設計選択である。

この選択により、本エコシステムは ConceptNet が苦手とする領域（人文学・古典・非西洋哲学など）でも構造化を保てる。一方、ConceptNet が圧倒的に強い「常識的関連性の汎用検索」は対象外として割り切る。両者の関係は競合ではなく、住み分けに近い。

CHAPTER 02

自己観察メタ DB ─ AWS Agent Registry・Portkey・MLflow の方向性を翻訳する

AWS Agent Registry（2024 preview）は、エージェント定義のクラウド集約管理という方向性を業界に提示した先駆プロジェクトである。エージェント・スキル・ツール・MCP サーバを 4 層メタデータで管理し、IAM 統合による承認ワークフローと semantic search を実装した。Portkey Agent Gatewayは、組織内の全エージェントを中央レジストリで管理し、アクセス制御・ガバナンス・権限を一体化する SaaS を展開している。MLflow Prompt Registry / Model Registryは、プロンプト・モデル成果物の版管理と Linked Foundation Model 配下のオープンソース基盤を提供する。OpenAI Agents SDK と Anthropic Claude Skillsは、API レベルでエージェント定義のパッケージ化を進めている。

本エコシステムの AR-DB は、これら先行事業が示した「エージェント定義の構造化メタ DB」という方向性を、ローカル SQLite に翻訳した実装にあたる。クラウド API ではなく SQL 直接照会（agents 448 / agent_relations 1,874 / db_references 518 / agent_tools 1,353 / tools 46）、手動登録ではなくファイル変更からの自動同期（~/.claude/settings.json の PostToolUse hook 9 件 / 10 秒 debounce）を採った。エージェント間関係は 9 種類に typed されており、calls（1,110）・orchestrates（222）・aggregates（183）・extends（108）・observed_by（77）・governed_by（73）・replaces（59）・delegates_to（27）・alias_of（15）と分布する。

AWS が「クラウド集約 × 承認ワークフロー」を選んだのに対し、本エコシステムは「ローカル自律 × 自動同期 × SQL 自由照会」を選んだ。これは個人運用環境の制約から生まれた設計選択であり、AWS と競合せず、補完関係に立つ。Model tier 別の運用（opus 38 / sonnet 75 / haiku 8）も AR-DB から直接照会可能であり、コスト最適化と判断品質のトレードオフが SQL レベルで可視化されている。

CHAPTER 03

多層階層メタオーケストレーション ─ ChatDev・AgentOrchestra の系譜を 5 層に展開する

ChatDev（OpenBMB）は、CEO オーケストレーター層 + designers / developers / testers の 2 層構造で、マルチエージェント協業によるソフトウェア開発を実証した。AgentOrchestra（arXiv 2506.12508, 2025）は、階層型マルチエージェントフレームワークを理論的に整理し、上位エージェントが下位エージェントの能力を動的に組み合わせる設計を提示した。これらは「メタオーケストレーション層を明示的に持つ」という方向性を切り拓いた重要な系譜である。

本エコシステムはこの系譜を 5 層（Tier -1〜3）に展開した。Tier -1 meta（34 体、全エコシステムを横断する判断層）、Tier 0 orchestrator（27 体、/db-master / /dbo / /process-orchestrator 等の最上位指揮）、Tier 1 team（26 体、領域メタ /dom-science / /dom-society 等 6 領域 + 連載チーム）、Tier 2 specialist（110 体、個別 DB エージェント + 編集部）、Tier 3 utility（251 体、検索・整形・保存等の道具的役割）。総 448 アセットがこの 5 層で配置される。

特徴は型自動判定の組込みにある。/db-master はユーザーの DB 構築要求を受け取り、概念 DB（/adb）・実データ DB（/db-blindspot + /db-build）・既存深化（/ddb）の 3 経路を自動判定する。ChatDev の CEO は単一プロジェクト内の役割分担を行うが、本エコシステムの Tier 0 はプロジェクト類型そのものを判定してルーティングする。この設計選択は、領域別 DB の数（30+）が前提として大きいことから生まれた必然である。

CHAPTER 04

学術正本層との接続 ─ OpenAlex・Wikidata・ORCID・ROR を基盤として組み込む

OpenAlex（2022, OurResearch）は、廃止された Microsoft Academic Graph の後継として、Crossref・ORCID・ROR を統合した約 2.5 億 works の学術メタデータを CC0 ライセンスで公開する。S3 バケットでの 330 GB bulk snapshot を四半期ごと無料配布し、API は 100K req/日まで無料で利用可能。Wikidataは 1.15 億エンティティ・14 億 statements を 380+ 言語で抱える Wikimedia Foundation 運営の構造化ナレッジベース。ORCIDは研究者の永続的識別子、RORは研究機関の永続的識別子として、それぞれの領域でデファクト標準を確立している。

本エコシステムは、これらを学術領域の正本層として組み込む方針を採っている。実際、167 DB のうち 23+ DB が openalex_id 列をスキーマに実装済。academic-landscape-db は 233,779 ジャーナル中 215,983 件（92.4%）に OpenAlex ID を充填済。academic-outcomes-db には専用の 4 phase ETL（phase1_openalex_pilot → phase2b_openalex_recent → phase5_openalex_1980_99 → phaseProd_fill_15_domains）が稼働。FTT-DB v2 は 18,524 件の OpenAlex 論文を統合済。CQ-DB は 7,082 研究者中 3,496 件（49.4%）に紐付けが進む。

住み分けは明確だ。OpenAlex が「論文・著者・機関の正本」を担い、本エコシステムは「意味構造（subfield / 系譜 / 概念関係）」を担う。両者を openalex_id という Linked Data 識別子で接続することで、学術領域での内部 DB の規模制約を OpenAlex 側に逃がしつつ、本エコシステムの構造化価値を保てる。

CHAPTER 05

LLM-native 知識基盤 ─ Karpathy・WeKnora・AGENTiGraph の系譜に位置する

Andrej Karpathy（旧 OpenAI/Tesla）が 2024 年に Gist で提示した「LLM-maintained wiki」の概念は、知識基盤を人間が更新するのではなく、LLM エージェントが継続更新する self-evolving モデルを示した。WeKnora（Tencent）は、エンタープライズ向けに Document + Entity + Relation を multi-agent orchestration で統合する OSS を展開する。AGENTiGraph（arXiv 2508.02999, 2025）は、エージェントが知識グラフを動的に拡張する task routing 設計を提案している。これらは「LLM-native」な知識基盤の系譜である。

本エコシステムはこの系譜に明確に属する。167 独立 DB × 各 DB 専属エージェント × cross_db_refs という構成は、Karpathy の LLM-maintained wiki を個人運用環境で実装した形態にあたる。各 DB の構築・更新・品質検証は、db-concept-builder / db-timeseries-builder / db-people-builder / db-network-builder 等のドメイン特化ビルダーエージェントが分担する。db-quality-auditor は独立監査の役割を担い、生成と検証の分離（メタ原則）を構造化する。

規模は WeKnora（エンタープライズ、3-5 エージェント）の規模感とは異なる。Karpathy の提案も個別 wiki 単位だった。本エコシステムは個人 + LLM 環境で 100+ エージェントを同時運用する密度で、この系譜の個人スケール実装に位置する。

CHAPTER 06

運用規律の組合せ密度 ─ 単一構造ではなく密度で輪郭を持つ

本エコシステムの輪郭は「単一構造の新規性」ではなく「運用規律の組合せ密度」にある。以下、5 種の規律を列挙する。

(1) DB 単位の IRR Cohen's Kappa 公表。物理 DB の Kappa 0.8745、宇宙地球史 DB の 0.9863、地球科学 DB の 0.9550、植物学 DB の 0.8602、時間概念 DB の 0.97 等、複数 DB で個別に inter-rater reliability を測定・公表する。学術 KG では Semantic Scholar の一部例外を除き、ほぼ前例がない実践である。

(2) source_url 列スキーマ必須化。全 DB の主要レコードに source_url を強制する。PHYS / CEH / ES / CQ 等で 100% 充填、academic-landscape-db で 92.4%。これは OpenAlex・Wikidata の references 設計を内部 DB レベルに継承した実装である。

(3) path-1（LP as truth）ルール。多層文書（LP / Book / 詳細）が並存する場合、LP を正本とし内側層を追随させる原則。7+1 問いランディングで実証済。

(4) 3 経路必須提示ルール。DB 構築の意思決定時、/adb（概念 DB）/ /db-blindspot+/db-build（実データ DB）/ /ddb（既存深化）の 3 経路を必ず明示提示する。meta-principles-enforcer が違反を検出する。

(5) Production-grade 完備基準（Pilot 思考禁止）。各領域 publications 1,500+ / 主要エンティティ 300+ を絶対達成基準として運用。MVP・Pilot・Mid・Production の階層表現を排除する。

これらの規律は、個々には他所に類例がある。だが個人 + LLM 運用環境で同時に運用する密度は、市場の主流（runtime tracing 偏重 / 単一グラフ偏重 / Pilot 思考）から見て uncommon である。これが本エコシステムの輪郭を形作る。

EPILOGUE

位置づけの輪郭 ─ 翻訳としての実装

本エコシステムは、ConceptNet が拓いたパターン C 連邦の系譜にあり、AWS Agent Registry が示した自己観察メタ DB の方向性をローカル翻訳し、ChatDev・AgentOrchestra の階層メタ系譜を 5 層に展開し、OpenAlex を学術正本層として接続し、Karpathy・WeKnora の LLM-native 系譜に個人スケールで属する。

世界初の主張は適切ではない。最も誠実な記述は、「先行事業が拓いた地平に立ち、Claude Code + ローカルファイル運用という特殊な環境に固有の運用規律として翻訳した実装」である。

この立ち位置は、ConceptNet・Wikidata・OpenAlex のような世界的インフラと並ぶものではない。それらの規模には及ばない。だが、それらが拓いた地平の上で、個人 + LLM が運用できる密度で領域別構造化を実践する輪郭は持つ。先行事業との関係は、競合ではなく、地平の上での独自配置にある。
