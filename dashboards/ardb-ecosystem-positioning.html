AR-DB エコシステムの運用特徴と先行事業との関係性

ミラツク/esse-sense DB エコシステム（AR-DB + 167 DB / 448 アセット）の運用特徴を、世界の優れた先行事業 ConceptNet・AWS Agent Registry・ChatDev・OpenAlex・WeKnora 等との関係性に位置づけて 5,000 字で解説する。

2026-05-18 作成 Yuya Nishimura + Claude Opus 4.7 5,000字 / 6章
PROLOGUE

立ち位置 ─ 先行の地平に立つ

本エコシステムは、世界の知識基盤プロジェクトが切り拓いた地平の上に立っている。ConceptNet が 27 年、Wikidata が 14 年、OpenAlex が 4 年、AWS Agent Registry が 2 年と、各分野には強力な先行事業がある。本レポートは「世界初」を主張するためのものではない。各先行事業と並ぶ輪郭で、本エコシステムが採った設計選択と運用上の特徴を 6 領域に分けて記述する。各章で先行事業を必ず参照し、その地平の上で何を選択したかを明示する。

CHAPTER 01

領域別独立 DB 連邦 ─ ConceptNet・ASER のパターン C を継承する

本章のキーワード「パターン C」とは、知識基盤を 1 つの巨大グラフに統合せず、領域別の独立テーブルを横断的な関係種別で接続する設計を指す。ConceptNet と ASER がこのパターンの代表である。

ConceptNet（MIT Media Lab, 1999-）は、1999 年に Push Singh と Marvin Minsky が始めた Open Mind Common Sense を起点に、27 年をかけて 3,400 万関係・304 言語の常識知識グラフを構築した。Robyn Speer 主導の AAAI 2017 論文で世界的に認知され、Numberbatch 単語埋め込みは意味類似度課題で世界水準を実証した。ConceptNet が確立した設計はまさに上記パターン C である。ASER（HKUST）が出来事領域でこれを継承し、USC ISI の CSKG（2021）は ConceptNet・ATOMIC・Wikidata-CS・WordNet・Roget・Visual Genome を統合した 6 ソース連邦の代表例となった。

本エコシステムも同パターン C に分類される。167 の独立 SQLite が、各々独自のスキーマを保ち、横断参照テーブル（cross_db_refs）で意図的に接続される。差異はひとつ。ConceptNet が汎用 34 関係種別に統一するのに対し、本エコシステムは領域別に関係種別を正規化する。物理学概念基盤では「先行概念 / 後継概念 / 理論的基盤」、人物基盤では「影響を受けた / 分派した / 統合された」、産業基盤では「供給された / 競合した」といった具合に、領域に最適化された関係語彙を持つ。これは ConceptNet が獲得した「汎用性」を犠牲にする代わりに、「専門性の解像度」を取る設計選択である。

この選択により、本エコシステムは ConceptNet が苦手とする領域（人文学・古典・非西洋哲学など）でも構造化を保てる。一方、ConceptNet が圧倒的に強い「常識的関連性の汎用検索」は対象外として割り切る。両者の関係は競合ではなく、住み分けに近い。

CHAPTER 02

自己観察メタ DB ─ AWS Agent Registry・Portkey・MLflow の方向性を翻訳する

AWS Agent Registry（2024 年公開予告）は、エージェント定義のクラウド集約管理という方向性を業界に提示した先駆プロジェクトである。エージェント・スキル・ツール・MCP サーバを 4 層のメタデータで管理し、IAM 統合による承認手続きと意味的検索を実装した。Portkey Agent Gatewayは、組織内の全エージェントを中央レジストリで管理し、アクセス制御・統制・権限を一体化する商用クラウド基盤を展開している。MLflow Prompt Registry / Model Registryは、プロンプト・モデル成果物の版管理と Linux Foundation 配下のオープンソース基盤を提供する。OpenAI Agents SDK と Anthropic Claude Skillsは、開発者向けインターフェースの水準でエージェント定義のパッケージ化を進めている。

本エコシステムの AR-DB は、これら先行事業が示した「エージェント定義の構造化メタ DB」という方向性を、ローカル SQLite に翻訳した実装にあたる。具体的には、エージェント 448 体・関係 1,874 件・DB 参照 519 件・ツール接続 1,353 件を SQL で直接照会できる。ファイル変更時には内部設定ファイルに置かれたツール実行後フック 9 件が、10 秒の遅延制御を介して DB を自動的に再構築する。エージェント間の関係は呼び出し・統括・集約を中心に 9 種に類型化されている。

AWS が「クラウド集約 × 承認手続き」を選んだのに対し、本エコシステムは「ローカル自律 × 自動同期 × SQL 自由照会」を選んだ。これは個人運用環境の制約から生まれた設計選択であり、AWS と競合せず、補完関係に立つ。モデル階層別の運用（opus 38 / sonnet 75 / haiku 8）も AR-DB から直接照会可能であり、費用最適化と判断品質のトレードオフが SQL の水準で可視化されている。

CHAPTER 03

多層階層メタオーケストレーション ─ ChatDev・AgentOrchestra の系譜を 5 層に展開する

ChatDev（OpenBMB）は、CEO 役の統括エージェント層と設計者・開発者・検証者の 2 層構造で、複数エージェント協業によるソフトウェア開発を実証した。AgentOrchestra（arXiv 2506.12508, 2025）は、階層型の複数エージェント枠組みを理論的に整理し、上位エージェントが下位エージェントの能力を動的に組み合わせる設計を提示した。これらは「メタ統括層を明示的に持つ」という方向性を切り拓いた重要な系譜である。

本エコシステムはこの系譜を判断・指揮・チーム・専門・道具の 5 層に展開した。判断層は全エコシステムを横断するメタ層、指揮層は最上位オーケストレーター、チーム層は 6 領域のメタと連載チーム、専門層は個別 DB エージェントと編集部、道具層は検索・整形・保存などの基礎機能を担う。総 448 のアセットがこの 5 層で配置される（内訳は後掲の図解を参照）。

特徴は型自動判定の組込みにある。最上位の DB 構築指揮役は要求を受け取った瞬間、概念 DB 構築・実データ DB 構築・既存 DB 深化の 3 経路を自動的に判定し、適切な下位エージェント群へ振り分ける。ChatDev の CEO 役は単一プロジェクト内の役割分担を行うが、本エコシステムの最上位指揮層はプロジェクト類型そのものを判定して振り分ける。この設計選択は、領域別 DB の数（30 を超える）が前提として大きいことから生まれた必然である。

CHAPTER 04

学術正本層との接続 ─ OpenAlex・Wikidata・ORCID・ROR を基盤として組み込む

OpenAlex（2022 年, OurResearch）は、廃止された Microsoft Academic Graph の後継として、Crossref・ORCID・ROR を統合した約 2.5 億件の学術成果メタデータを CC0 ライセンスで公開する。S3 配下に 330 GB の一括スナップショットを四半期ごと無料配布し、接続インターフェースは 1 日 10 万要求まで無料で利用可能。Wikidataは 1.15 億の対象項目・14 億の言明を 380+ 言語で抱える Wikimedia Foundation 運営の構造化知識基盤。ORCIDは研究者の永続的識別子、RORは研究機関の永続的識別子として、それぞれの領域で事実上の標準を確立している。

本エコシステムは、これらを学術領域の正本層として組み込む方針を採っている。174 ある DB のうち 23 以上が OpenAlex 識別子をスキーマに実装済で、学術領域系では充填率が 9 割を超える DB も複数ある。たとえば学術全体地図 DB は 233,779 ジャーナル中 21 万件超に OpenAlex 識別子を紐付け、未来技術動向 DB は 18,524 件の OpenAlex 論文を統合済である。学術成果 DB には専用の取り込みパイプラインが 4 段階で稼働し、月次差分も追従する。

住み分けは明確だ。OpenAlex が「論文・著者・機関の正本」を担い、本エコシステムは「意味構造（下位領域 / 系譜 / 概念関係）」を担う。両者を OpenAlex 識別子で接続することにより、学術領域の規模は OpenAlex に委ね、本エコシステムは構造化に集中する戦略が成立する。

CHAPTER 05

LLM-native 知識基盤 ─ Karpathy・WeKnora・AGENTiGraph の系譜に位置する

Andrej Karpathy（旧 OpenAI / Tesla）が 2024 年に短い覚書として公開した「LLM が維持するウィキ」の概念は、知識基盤を人間が更新するのではなく、LLM エージェントが継続的に更新する自己進化型モデルを示した（個人の覚書という性格のため、査読論文より軽い典拠ではあるが、概念提示としては影響力が大きい）。WeKnora（Tencent）は、企業向けに「文書 + 実体 + 関係」を複数エージェント協調で統合するオープンソースを展開する。AGENTiGraph（arXiv 2508.02999, 2025 年 8 月公開）は、エージェントが知識グラフを動的に拡張する設計を提案している。これらは「LLM ネイティブ」な知識基盤の系譜である。

本エコシステムはこの系譜に明確に属する。167 独立 DB × 各 DB 専属エージェント × 横断参照という構成は、Karpathy の LLM 維持型ウィキを個人運用環境で実装した形態にあたる。各 DB の構築・更新・品質検証は、概念ビルダー・時系列ビルダー・人物ビルダー・ネットワークビルダー等の領域特化エージェントが分担する。品質監査エージェントは独立監査の役割を担い、生成と検証の分離（メタ原則）を構造化する。

規模は WeKnora（企業向け、3〜5 エージェント）の規模感とは異なる。Karpathy の提案も個別ウィキ単位だった。本エコシステムは個人 + LLM 環境で 100 以上のエージェントを同時運用する密度で、この系譜の個人スケール実装に位置する。

CHAPTER 06

運用規律の組合せ密度 ─ 単一構造ではなく密度で輪郭を持つ

本エコシステムの輪郭は「単一構造の新規性」ではなく「運用規律の組合せ密度」にある。以下、5 種の規律を列挙する。

(1) DB 単位の評価者間一致度を公表する。複数の評価者が同じ判定に至る度合いを示す指標（Cohen のカッパ係数）を、DB ごとに個別に測定し公表する。0.8 を超えると「ほぼ完全な一致」とされる業界標準において、物理 DB は 0.87、宇宙地球史 DB は 0.99、地球科学 DB は 0.96、植物学 DB は 0.86、時間概念 DB は 0.97 を達成している。学術知識グラフでは Semantic Scholar の一部例外を除き、ほぼ前例がない実践である。

(2) 出典 URL 列の必須化。全 DB の主要レコードに出典 URL を強制する。物理・宇宙地球史・地球科学・現代の問い等で 100% 充填、学術全体地図 DB で 92.4%。OpenAlex・Wikidata の参照設計を内部 DB の水準に継承した実装である。

(3) ランディング正本ルール。多層の文書（ランディング / 書籍 / 詳細）が並存する場合、ランディングを正本とし内側層を追随させる原則。「7+1 の問い」ランディングで実証済。

(4) 3 経路必須提示ルール。DB 構築の意思決定時、概念 DB 構築・実データ DB 構築・既存 DB 深化の 3 経路を必ず明示提示する。メタ原則順守監視エージェントが違反を検出する。

(5) 本番水準を初手から目標とする。試作・中規模・本番という段階表現を排し、各領域で論文 1,500 件以上・主要エンティティ 300 件以上を初期から達成基準として運用する。

これらの規律は、個々には他所に類例がある。だが個人 + LLM 運用環境で同時に運用する密度は、市場の主流（実行時計測への偏り / 単一グラフへの偏り / 試作思考）から見て稀少である。これが本エコシステムの輪郭を形作る。

EPILOGUE

位置づけの輪郭 ─ 翻訳としての実装

本エコシステムは、ConceptNet が拓いたパターン C 連邦の系譜にあり、AWS Agent Registry が示した自己観察メタ DB の方向性をローカル環境に翻訳し、ChatDev・AgentOrchestra の階層メタ系譜を 5 層に展開し、OpenAlex を学術正本層として接続し、Karpathy・WeKnora の LLM ネイティブ系譜に個人スケールで属する。

世界初の主張は適切ではない。最も誠実な記述は、「先行事業が拓いた地平に立ち、Claude Code + ローカルファイル運用という特殊な環境に固有の運用規律として翻訳した実装」である。

この立ち位置は、ConceptNet・Wikidata・OpenAlex のような世界的な基盤と並ぶものではない。それらの規模には及ばない。だが、それらが拓いた地平の上で、個人 + LLM が運用できる密度で領域別の構造化を実践する輪郭は持つ。先行事業との関係は、競合ではなく、地平の上での独自配置にある。

このエコシステムに接触する読者は、3 つの実用接点を持つ。研究者は自分の専門領域に最も近い DB（30 を超える領域別 DB から選択）に問いを投げて系譜・概念関係・典拠を取り出せる。経営者は「事業仮説 → 候補研究者抽出 → 構造化提案」の 2 段階回答を AR-DB 経由で得られる。技術者は AR-DB の SQL スキーマを参考に、自組織のエージェント定義を構造化メタ DB として実装する設計案を取得できる。先行事業との関係を地平とし、本エコシステムは個別の問いに対する翻訳装置として機能する。
