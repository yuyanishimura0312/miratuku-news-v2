第1章 決済システム構造

価値の最終決済を担う大口決済インフラ。グロス決済とネット決済、決済ファイナリティ、システミックリスクを扱う。

系譜ハワラ(8世紀)や中国の票号は、物理的資金移動を避け двусторонの債務を定期的にネッティングする信用送金として発達した。近代の清算機関(1853)が多者間ネッティングを制度化、DNSがそれを電子化、CLSがFXにPvPを導入した。『相殺で決済する』という同型の原理が文化と時代を超えて反復する。

主要概念

流動性リサイクリング Liquidity recycling production_live

流動性リサイクリングは、決済システム内で受け取った資金を参加者が直ちに次の支払へ回すことで、同じ流動性が複数の決済を順次支える効果をいう。RTGSでは各支払が個別に最終化されるため本来多くの日中流動性を要するが、入金を滞留させず再利用すれば、外部から投入する担保や中央銀行与信を抑えられる。キュー管理、相殺アルゴリズム、参加者の早期支払行動と相性がよく、決済効率と金融安定を両立させる考え方である。一方で、参加者が不確実性を恐れて入金を留保すると効果は低下する。大口支払の偏り、時点集中、信用不安、ネットワーク分断があると、再循環は期待通り働かない。

流動性シンク (資金滞留) Liquidity sink production_live

流動性シンクは、決済システム内である参加者が入金を受け取っても、それを次の支払に回さず保蔵することで、他参加者が利用できる日中流動性を吸収してしまう現象である。RTGSでは支払が逐次かつ総額で決済されるため、受領資金の再利用が全体効率を左右する。大口受取者が支払を遅らせると、待ち行列が伸び、他行は追加担保や中央銀行信用を必要としやすくなる。この概念は参加者行動がシステム流動性に与える外部性を説明するうえで重要である。一方で、支払停止が常に悪いとは限らず、信用不安、オペレーション障害、制裁確認、リスク管理上の正当な保留と区別する必要がある。

即時グロス決済 (RTGS) Real-Time Gross Settlement production_live

RTGS は支払指図を受信した瞬間に1件ずつ中央銀行当座預金を借記・貸記し、決済を即時かつ最終 (irrevocable) とする方式。ネット決済 (DNS) が日中の相殺で流動性を節約する代わりに決済までエクスポージャを抱えるのに対し、RTGS は各取引で全額の流動性を必要とするがHerstatt型の信用リスクを構造的に排除する。Fedwire・TARGET2・BOJ-NET・CHAPS 等が代表。流動性とリスクのトレードオフが設計の中心問題で、後年 hybrid/LSM が両者の折衷を図った。

日中与信 (中央銀行) Intraday central bank credit production_live

日中与信は、RTGSなど即時グロス決済に参加する金融機関が、支払指図の時間差で一時的に資金不足となる場合に中央銀行から受ける日中の流動性供給である。当座貸越、日中レポ、担保差入れなどの形をとり、営業終了時までに返済されることを前提に設計される。これにより参加者は入金を待って支払いを滞らせる必要が減り、決済キューの滞留やシステム全体の流動性不足を緩和できる。一方で、担保要件が厳しすぎれば利用可能性が下がり、緩すぎれば中央銀行の信用リスクやモラルハザードを招く。

決済ファイナリティ Settlement Finality standard_spec

ファイナリティは『いつ支払が確定し巻き戻せなくなるか』を定義する。EU 決済ファイナリティ指令 (1998) は zero-hour rule (破綻当日0時に遡って取引を無効化する破産法理) を排除し、システム内の決済を保護した。技術的ファイナリティ (記帳完了) と法的ファイナリティ (倒産法上の保護) を区別する。分散台帳では確率的ファイナリティ (Nakamoto) と決定的ファイナリティ (BFT) の差として再登場する。

流動性プーリング Liquidity pooling production_live

流動性プーリングは、銀行グループや企業グループ内の複数口座に分散した資金余力を一体的に把握し、日中決済や資金繰りに使えるようにする管理手法である。実際に残高を集約する物理的プーリングと、残高は分けたまま相殺・限度管理で効果を得る名目的プーリングがある。大口決済や証券決済では、参加者が個別口座ごとに過大な予備資金を置かずに済み、流動性コストや決済遅延を抑える意義がある。一方で法域をまたぐ場合は相殺の法的有効性、担保権、税務、規制資本、破綻時の資金帰属が問題となり、単純な残高共有として扱うとリスクを見誤る。

流動性ブリッジ Liquidity bridge pilot

流動性ブリッジは、複数のRTGSや通貨圏、時差のある決済基盤の間で、参加者が日中流動性をより柔軟に配置・移転できるようにする接続概念である。単一市場内で資金が滞留すると、支払待ち行列や担保需要が増え、クロスボーダー決済では時差と通貨ごとの流動性断片化が障害になる。ブリッジは、口座、担保、支払指図、場合によってはPvPやDvPの条件を連携させ、必要な場所へ流動性を届ける設計を目指す。一方で、法域間の最終性、中央銀行口座へのアクセス、担保評価、オペレーショナルリスク、相互依存による障害伝播が難点であり、単なる技術接続だけでは流動性コストを消せない。

流動性予約 Liquidity reservation production_live

流動性予約は、参加者が保有する中央銀行マネーや決済口座残高の一部を、特定の支払、決済サイクル、システム上重要な取引に優先的に使えるよう取り分ける機能である。RTGSやハイブリッド決済では、全支払が同じ資金プールを奪い合うと重要決済が待ち行列に埋もれ、連鎖遅延を招くことがある。予約により証券決済、CLS型の外為決済、緊急支払などの完了可能性を高められる。一方で、資金を細かく囲い込むと全体の流動性効率が下がり、未使用予約が他の支払を阻害するため、優先順位、解放条件、監視が設計上の焦点となる。

流動性節約メカニズム Liquidity Saving Mechanism production_live

流動性節約メカニズムは、RTGSで即時に単独決済できない、または流動性を節約したい支払をキューに置き、参加者間で相殺できる支払の組合せを見つけて同時にグロス決済する仕組みである。各支払は法的には個別の中央銀行貨幣移転として処理されるが、同時解放により必要な日中流動性や担保を抑えられる。大口決済では、流動性コストと決済遅延リスクの均衡を取る機能として重要である。一方、キュー設計が悪いと支払の先送り、戦略的待機、参加者間の公平性問題を招き、単純な即時性とは緊張関係に立つ。

中央流動性管理 Central liquidity management production_live

中央流動性管理は、中央銀行口座上の資金を一元的に把握し、RTGS、証券決済、担保管理、周辺サービスへ必要な流動性を配分する仕組みである。T2のような構成では、参加者は中央の流動性管理口座を起点に、決済サービスごとの専用口座へ資金を移し、日中の支払需要や証券引渡しに応じて調整する。これにより、分散した残高の遊休化を抑え、中央銀行業務と市場インフラの連携を明確にできる。一方で、運用障害や接続不備が広範な決済機能に波及しやすく、権限管理、業務継続、参加者側の資金予測能力が不可欠である。

関連する数式

RTGS 必要流動性 (最大累積ネットデビット)
L = \max_{t}\sum_{i:\,t_i \le t}(P_i^{out}-P_i^{in})
例: 入出金の時系列でピーク累積デビット=50→残高/与信50必要。順序最適化で低減可。
ヘルシュタット・エクスポージャ
E = \sum_k A_k\,\mathbb{1}[t^{pay}_k < t^{recv}_k]
例: 先払い3件×各$10M → E=$30M がHerstattリスク。CLSで除去。
決済ネットワーク媒介中心性
C_B(i)=\sum_{s\ne t}\frac{\sigma_{st}(i)}{\sigma_{st}}
例: コア銀行は高中心性=システミック重要。
流動性カバレッジ比率(LCR)
\text{LCR}=\frac{\text{HQLA}}{\text{Net outflows}_{30d}}\ge1
例: バーゼルIIIの流動性規制。

第2章 銀行間メッセージング規格

ISO 20022・ISO 8583・SWIFT 等、決済指図を運ぶメッセージ標準。構造化データがAMLとSTPを左右する。

系譜SWIFT MT(1977)が銀行間メッセージを、ISO8583(1987)がカードを標準化、ISO20022(2004)が構造化XMLを導入、CBPR+(2022)がクロスボーダー移行を進め、2025年にMTからMXへ全面移行する。

主要概念

ISO8583 MTI ISO 8583 Message Type Indicator production_live

ISO8583のMTIは、カード取引メッセージの先頭付近に置かれる4桁のMessage Type Indicatorであり、メッセージの版、機能、発信主体、応答か要求かを示す。これにより、認可要求、認可応答、金融取引、取消、照会、ネットワーク管理などの処理経路を受信側が判別し、後続のビットマップとデータ要素をどの意味で解釈するかを決める。カード決済では加盟店端末、アクワイアラ、スイッチ、国際ブランド、イシュアが多数接続されるため、MTIは相互運用の入口となる重要な分類子である。ただし、MTIだけで取引の全内容は分からず、処理コード、金額、時刻、加盟店情報、応答コードなどのデータ要素と組み合わせる必要がある。実装やネットワークごとの方言もあり、単純な4桁として過信できない。

MXメッセージ MX message production_live

MXメッセージは、ISO 20022に基づくXML形式の金融メッセージ群で、支払指図、入出金通知、照会、証券関連通知などを構造化されたデータ要素で表現する。従来のMT型メッセージより情報量が多く、送金人・受取人情報、規制対応項目、照合に使う参照情報を機械処理しやすいため、クロスボーダー決済の透明性や自動処理率の改善に重要である。一方で、XMLは冗長で移行負荷が高く、同じISO 20022でも市場慣行や実装ガイドの差により相互運用性が完全には保証されない。

DE55 (ICCデータ) ISO 8583 DE55 ICC data production_live

ISO 8583のDE55は、EMVチップ取引で生成されるICC関連データを、カード承認メッセージ内で発行者側へ運ぶためのデータ要素である。端末はカードから読み出したタグ、暗号文、端末検証結果、取引条件などをTLV形式で組み立て、アクワイアラ、スイッチ、ブランド網を通じてイシュアに送る。これにより磁気ストライプ時代より強い動的認証とリスク判定が可能になり、対面カード決済の不正抑止に不可欠となった。一方で実装差、タグ解釈、データ長、ルーティング途中の変換に弱く、DE55が存在しても端末・カード・イシュアの全体設定が不適切なら安全性は低下する。

ISO8583 ビットマップ ISO 8583 bitmap production_live

ISO 8583のビットマップは、カード決済メッセージ内でどのデータ要素が存在するかをビット列で示すフィールド指示子である。各ビットが取引金額、加盟店情報、認証データ、応答コードなどの要素番号に対応し、受信側はビットマップを読んで後続フィールドを解釈する。これにより、可変的なカード取引情報を効率的に詰め込み、ネットワーク間で高速に処理できる点が重要である。一方、要素定義や拡張領域の運用はスキームやプロセッサごとに差があり、同じビット構造でも実装差が相互接続の障害になり得る。可読性も高くないため運用解析には専門知識が要る。

ISO 8583 (カード取引メッセージ) ISO 8583 production_live

ISO 8583 は bitmap でどの data element (DE) が存在するかを示す効率的なバイナリ/ASCII 形式。DE2=PAN, DE3=processing code, DE4=amount, DE39=response code 等。Visa/Mastercard/各国スキームが方言を持つ。低レイテンシ authorization に最適化され、現在もカードネットワークの authorization レイヤを支配する。

インドのISO20022採用 ISO 20022 adoption (India) production_live

インドのISO 20022採用は、RTGSやNEFTなどの決済システムで、支払指図や関連情報を豊富な構造化データとして扱う方向への移行を指す。ISO 20022はXML等のデータモデルを通じ、送金人・受取人情報、目的コード、照合情報などを機械処理しやすくし、直通処理、AML確認、企業の入金消込、システム間連携を改善する。インドのように大規模で多様な決済参加者を持つ市場では、共通語彙を整える意義が大きい。ただし標準採用だけで業務品質が上がるわけではなく、入力データの欠落、旧システムとの変換、参加者ごとの実装差、例外処理の運用が残れば、期待された効率化は限定的になる。

ISO 20022 (金融メッセージ規格) ISO 20022 production_live

ISO 20022 はメッセージ定義をビジネスモデル層と構文層に分離した『標準を作る標準』。送金は pacs.008 (FI-to-FI customer credit transfer)、顧客起点は pain.001、報告は camt.05x。SWIFT MT (固定長・略号) に比べ、受取人情報・規制データ・目的コードを構造化でき、AML や straight-through processing を改善する。2022-2025 に SWIFT は CBPR+ でクロスボーダーを MT から MX (ISO 20022) へ移行した。

ISO8583 リバーサル ISO 8583 reversal message production_live

ISO 8583のリバーサルは、カード取引などで承認や金融処理が途中失敗、タイムアウト、重複、取消となった場合に、先行メッセージの効果を取り消しまたは補正するためのメッセージである。端末、加盟店、アクワイアラ、ネットワーク、イシュア間で、元取引を識別する情報を付けて送信し、保留枠の解放や二重請求防止を図る。カード決済では通信断や応答不達が避けられないため、リバーサルは整合性維持の中核的な例外処理である。ただし、すべての状態不一致を即座に解消できるわけではなく、照合、チャージバック、返金、バッチ清算との関係を正しく扱う必要がある。

ISO20022グローバル移行 Global ISO 20022 migration production_live

ISO 20022グローバル移行は、各国のRTGS、大口決済、クロスボーダー決済、証券決済などが、従来の固定長・独自形式・MT系メッセージから、XMLを中心とする構造化されたMXメッセージへ移る流れである。より豊富な送金目的、当事者情報、規制関連情報を標準化して運べるため、STP、AML対応、照合、データ分析の改善が期待される。決済インフラの相互運用性を高める一方、移行は単なるフォーマット変更ではなく、業務項目、バリデーション、バックオフィス、顧客チャネルの改修を伴う。共存期間、各国仕様差、データ切り詰め、旧形式との変換品質が実務上の制約になる。

ISO20022 大口決済プラス ISO 20022 HVPS+ production_live

ISO 20022 HVPS+は、大口決済システムでISO 20022メッセージを一貫して使うための市場実務ガイドラインであり、資金移動、参加者識別、送金目的、規制関連情報などの項目を共通の解釈で実装することを狙う。中央銀行RTGSや国際銀行間決済の移行では、同じ標準でも各国で項目の使い方が割れると自動処理や照合が損なわれるため、HVPS+は相互運用性を補強する役割を持つ。ただし法的ルールそのものではなく、既存システム制約や移行期間の併存により完全な統一は難しい。

第3章 コルレス銀行・国際送金

ノストロ/ボストロ口座の連鎖で国境を越える送金。コスト・速度・透明性・デリスキングが課題。

系譜Herstatt破綻(1974)が決済時差リスクを露呈し、CLS(2002)がPvPで元本リスクを除き、SWIFT gpi(2017)が追跡性を、G20ロードマップ(2020)とmBridge(2022)がクロスボーダーPvPを進める。

主要概念

ノストロ/ボストロ口座 Nostro/Vostro accounts production_live

銀行Aが外国通貨で決済するには、その通貨国の銀行Bに口座を持つ必要がある。A視点でその口座は nostro (『我々の(あなたのところの)口座』)、B視点では vostro。クロスボーダー送金はこれら口座間の借記・貸記の連鎖として実現する。各 nostro には事前資金 (prefunding) が必要で、これが滞留コストとコルレス網の効率の中心問題となる。

SWIFT gpi (グローバル決済イニシアチブ) SWIFT gpi production_live

SWIFT gpi は Unique End-to-end Transaction Reference (UETR) を付与し、各ホップの状況をトラッカーで可視化、当日決済 (same-day value) とFX・手数料の透明化を義務付ける。従来の『送金がどこにあるか分からない』問題を解消し、G20 ロードマップが掲げる速度・コスト・透明性・アクセスの改善に資する。

送金回廊 (corridor) Remittance corridor production_live

送金回廊は、ある送出国から特定の受取国へ向かう国際送金の経路を指し、移民労働者送金、家族扶養、貿易小口支払いなどの流れを分析する単位である。同じ送金事業者でも、回廊ごとに為替流動性、規制要件、本人確認、提携銀行、現金受取網、競争環境が異なるため、手数料、所要時間、失敗率、受取方法が大きく変わる。決済政策では、平均的な国際送金ではなく回廊別にボトルネックを見ることが重要である。一方で回廊という分類は経路を単純化するため、中継銀行、プラットフォーム内振替、非公式送金、複数通貨経由の実態を十分に表せない場合がある。
